# 0단계 결과 기록

## 1차 — 2026-09-24, 테스트벤치

기기: Samsung SM-S948N, Android 17 (API 37), 1440x3120, 세로.  
설정: 감시 400ms, 탭 누름 30ms.

| 질문 | 결과 | 근거 |
|---|---|---|
| Q1 같은 창 보안 전환 감지 | **예** | `SUCCESS(#45) → SECURE_WINDOW(#45)` 2회, 직전 성공 후 +381ms / +391ms (감시 1주기 이내) |
| Q2 새 창 보안 전환 감지 | **예, 창 ID가 바뀜** | `SUCCESS(#45) → SECURE_WINDOW(#64)`. PLAN 2장 A 확인: 감시 중 창 ID를 고정하면 안 된다 |
| Q3 보안 창에 주입 탭 전달 | **예 (1회)** | 테스트벤치 `#3 … 주입 보안중`, 수신 좌표 (1047,2617) = 저장 좌표 |
| Q4 요청 간격 오류 | **0회 / 235회** | `INTERVAL_TIME_SHORT` 없음. 응답 시간 중앙 5ms, 최대 31ms |
| Q4 연타 전송 간격 | **100, 100, 100, 100ms** (2회차 모두) | 진단 앱 기준 전송 시각. 완료 콜백 +32~36ms |
| 뷰 보안 필터 영향 | **차단 의심, 재시험 필요** | 2차 참조 |
| 실제 대상 앱 (시험 B) | 미정 | 대상 앱 미정 |

기타 관찰
- 대상 앱이 전면이 아닐 때 `NO_TARGET_WINDOW`(91회)로 캡처를 건너뜀 — 의도대로.
- 비활성·비포커스(`--`) 상태의 대상 창도 캡처됨(알림창 등 위에 있을 때로 추정). 1단계에서는 활성 창일 때만 트리거하도록 한다.
- 감시 시작 시 이미 보안 상태인 경우가 있었음(11:06:58). 명세 기본값(정상 기준 확인 전에는 실행 안 함)이 필요함을 확인.
- 보고서의 "가동"은 서비스가 아니라 기기 가동 시간이다(표기 수정 예정).

## 2차 — 같은 날, 연타·필터

- 연타 2회(10탭) 모두 전송 간격 정확히 100ms.
- 테스트벤치: 창 수신 19 / **영역 수신 0** / 주입 10. 주입 탭 10개가 창까지는 왔으나 탭 영역 뷰가 하나도 받지 못함.
- 연타가 있던 동안 설정 기록: 가려짐 필터 켬 → 끔 → 접근성 민감 켬. 각 연타가 어느 설정에서 나갔는지 기록이 없어 필터별 판정 불가.
- 해석(검증 필요): Android 14+에서 `accessibilityDataSensitive`인 뷰(그리고 `filterTouchesWhenObscured`가 켜진 뷰는 기본값 AUTO에서 민감으로 취급될 수 있음)는
  접근성 도구가 아닌 서비스의 주입 터치를 버린다. 사실이라면 이런 속성을 쓰는 실제 앱(금융 앱 등)에서는 트리거탭의 탭이 무시된다.
  `isAccessibilityTool`을 허위 선언해 우회하지 않는다(명세 8장).
- 조치: 테스트벤치 0.0.2가 영역에서 버려진 터치를 `✗ 영역 미수신 … [가림필터, 민감]`으로 기록. 필터 끔 / 가림필터만 / 민감만 세 조건 재시험.
