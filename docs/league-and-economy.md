## 수치의 출처와 권위 (v0.2 에서 바뀐 것)

v0.1 의 수치는 전부 `tools/economy-sim/economy_sim.py`(승률 **로지스틱 근사**)에서 나왔다. 그 뒤 리그·경제 계층이
`web/engine/season.js` 에 **실제 `MatchSimulator` 위로** 구현되면서, 근사 위에서 잡은 초기값이 실제 엔진에서는
맞지 않는다는 것이 드러났다. v0.2 는 본문 수치를 실제 엔진 실측값으로 갈아 끼운 것이다.

| 층 | 스크립트 | 성격 | 이 문서에서의 지위 |
|---|---|---|---|
| **실제 엔진** | `node web/season-check.mjs` (n=200 · 3시즌 · seed 1 · 약 25초) | 진짜 `MatchSimulator` + 진짜 `TrainingSession` | **권위 있는 값.** A.3.1 · A.4 · B.3 의 수치는 전부 여기서 나온다 |
| 근사 모델 | `python3 tools/economy-sim/economy_sim.py` (n=500 · 6 시나리오 · 약 11초) | 승률 = `sigmoid(0.235 × ΔOVR)` · 졸업 OVR 회귀 모델 | **보조.** 천장 확률처럼 대량 표본이 필요한 계산과, 엔진에 없는 대조군(현행 프로토타입 규칙·정식 미션) 전용 |

두 값이 어긋나면 **엔진이 맞다.** 근사 모델이 남긴 차이는 B.3.1 아래 "근사 모델과의 차이"에 수치로 적어 두었다.

## A.1 참가 구조와 시즌 포맷

### A.1.1 참가 구조

`world.md` 1.2절의 "블룸 프로젝트" 설정을 그대로 쓴다. 리그는 6개 기존 구단 + 리그가 창단 특례로 승인한 **신생 구단(플레이어)** = **7팀**이다.

| 항목 | 값 | 근거 |
|---|---|---|
| 참가 팀 | 7 (플레이어 1 + AI 6) | `data/teams.json` 6구단 + 플레이어 구단 |
| 정규 포맷 | 더블 라운드로빈 (홈 1 · 원정 1) | 팀당 12경기 |
| 매치데이 | **14** | 홀수 팀이라 라운드마다 1팀 휴식(bye). 각 팀 bye 2회 |
| 경기 형식 | 5세트 3선승, 25점(5세트 15점), 2점차 | `match-sim.md` 4.1 그대로 |
| 홈/원정 | 라운드로빈 배정으로 홈 6 · 원정 6 균등 | 홈 이점은 A.3.4 |

> `world.md` 1.1절은 "6구단 5라운드 25경기"로 적혀 있다. 플레이어 구단이 들어오면 7팀이 되고, 5라운드(팀당 30경기)는 외곽 루프 시간(A.2)을 3배로 늘린다. **이 문서가 리그 포맷의 기준이며 `world.md` 1.1절은 세계관 텍스트로 읽는다** — 정식 서비스에서 시즌 길이를 늘릴 때 3라운드(팀당 18경기)까지가 상한이다(열린 이슈 D.2).

### A.1.2 승점과 순위 결정


|---|---|---|
| 1 | 승점 | |

## A.2 시즌 캘린더와 외곽 루프

### A.2.1 매치데이 = 세션 1회

**매치데이 하나가 플레이 세션 하나**다. 이것이 리그와 육성을 묶는 단위다.

```
[매치데이 N 시작]
  → 스카우트(보유 티켓 소진, 0~2회)            ~1분
  → 한계돌파(조각 30 이상이면)                  ~30초
  → 육성 1회 (스태미나 30)                      ~10분 (스킵 2분 / 자동 3.6분)
  → 라인업·전술 점검                            ~1분
  → 매치데이 경기 (자동 1분 / 관전 5분)          1~5분
  → 결과·보상 → 순위표 갱신
[매치데이 N+1 …]
```

| 항목 | 값 | 근거 |
|---|---|---|
| 매치데이당 육성 | **1회 (기준선)** | 시간 예산과 사다리 밸런스(A.4)를 이 값에 맞췄다 |
| 프리시즌 캠프 | 시즌 1 개막 전 **2회**만 | 튜토리얼 + 첫 로스터 확보. 시즌 2 이후의 프리시즌은 매치데이 루프에 흡수 |
| 시즌 1 총 육성 | **16회** (2 + 14) | 시뮬 기준선 |
| 매치데이 소요 | 수동 **≈ 15분** / 스킵·자동 **≈ 5분** | 육성 9.2분(training-mode 1.2) + 경기·기타 |
| 한 시즌 소요 | 수동 **≈ 3.5~4시간** / 자동 **≈ 1.2시간** | 14 매치데이 |
| 한 시즌 실시간 | **1~2주** (하루 1~2 매치데이) | GDD 1절 "중기 루프 1~2주" |

### A.2.2 스태미나와의 정합 (열린 이슈)

`training-mode.md` 10절: 육성 1회 = **스태미나 30**, 상한 **120**, 회복 **6분당 1**(하루 240).

| 계산 | 값 |
|---|---|
| 하루 자연 회복 | 240 (+ 일일 미션 30, 정식) = **270** |
| 이론상 하루 육성 | 270 / 30 = **9회** |
| 상한 120 의 제약 | 한 번 접속에 최대 4회 연속. 9회를 다 쓰려면 하루 3회 이상 접속 |
| 무과금 일일 기대 (training-mode 10절) | **3~4회** |

**즉 스태미나는 매치데이당 육성 1회를 강제하지 않는다.** 하루에 매치데이 1개만 진행해도 스태미나가 남고, 열심히 하는 유저는 매치데이당 3~4회 육성할 수 있다. 이것이 이 설계의 가장 큰 미해결 지점이다.

| 대응안 | 내용 | 판정 |
|---|---|---|
| **(a) 매치데이 게이팅** | 매치데이를 넘겨야 다음 육성 슬롯이 열린다(육성 1회/매치데이 하드 캡) | 스태미나가 무의미해지고 "하고 싶은데 못 한다"의 불만. **기각** |
| **(b) 남는 스태미나를 다른 소비처로** | 재육성·평가전 반복·연습경기·소재 던전에 스태미나를 쓰게 하고, **리그 로스터에 반영되는 육성은 매치데이당 1회만 대표 갱신 가능** | 유력. 대표 인스턴스 갱신에 쿨다운을 두는 셈 |
| **(c) 그냥 둔다** | 헤비 유저가 빨리 강해지는 것을 허용. 사다리 g 를 유저 진척도에 연동 | 라이브 서비스에서는 흔한 해법이지만 g 를 진척도 연동하면 "사다리" 서사가 깨진다 |

근사 모델에 매치데이당 육성 2회(라이트-헤비 중간) 시나리오를 넣어 영향을 측정했다: 같은 모델 안에서
**시즌 1 우승률 1% → 6%, 4강 7% → 18%, 시즌 3 우승률 16% → 32%** (B.3.5 표). 사다리가 대략 한 시즌 앞당겨진다.
(절대값은 근사라 엔진과 다르다 — 배율만 읽을 것.) **(b) 를 1순위로 두되 프로토타입에서는 (c) 로 두고 실측한다**(D.1 검증 항목).

### A.2.3 시즌 경계

```
매치데이 14 종료
  → [정규 시즌 결산] 최종 순위표 · 개인 기록(득점/블로킹/서브/리시브 1위) · 내 팀 시즌 리포트
  → [포스트시즌] (4위 이내일 때만 플레이, 아니면 관전/스킵 가능 — 보상은 순위 보상만)
  → [시즌 결산 화면] A.5.2
  → [사다리 상승] g += 11%p (시즌 4 부터는 상한 80% 라 증가 0), AI 구단 스탯 재계산, 연습생 7명 신규 세대로 교체
  → [프리시즌] 육성 1회 + 스카우트
  → 다음 시즌 매치데이 1
```

### A.2.4 라이브 서비스 시즌과의 대응

| 게임 내 | 라이브 운영 | 비고 |
|---|---|---|
| 블룸 리그 1시즌 (14 매치데이, 실시간 1~2주) | **시즌패스 1주기의 절반** | 패스는 2주 단위가 흔하다 |
| 시즌 사다리 g | **계정별로 진행**(서버 저장). 유저마다 시즌 번호가 다르다 | 랭킹은 g 가 아니라 "시즌 번호 + 승점"으로 매칭 |
| 시즌 랭킹 | 같은 시즌 번호끼리 승점·세트 득실 랭킹 | 사다리가 개인 진척도라 시즌 번호를 리그로 나눈다 |
| 픽업·이벤트 | **실시간 캘린더**(2~4주). 게임 내 시즌과 무관 | 픽업이 리그 시즌에 묶이면 운영이 경직된다 |

**핵심 결정: 게임 내 시즌은 개인 진척도, 라이브 시즌(패스·픽업·랭킹 기간)은 실시간 캘린더로 분리한다.** 두 개를 묶으면 늦게 시작한 유저가 시즌 1을 건너뛰어야 하거나, 빠른 유저가 기다려야 한다.

## A.3 AI 구단 규칙

### A.3.1 시즌 사다리 — 성장률 g

`prototype-play.md` 6.4 #1 의 관찰이 근거다. `players.json` 초기치 그대로면 연습생만으로도 6% 이기고 졸업생 6명이면 70~90% 이긴다. 잠재력 60% 성장이면 8회 육성해도 6~28%. 사다리는 이 구간을 시즌 단위로 늘려 놓기 위한 장치다.

```
실효 스탯(선수 p, 시즌 n) = round( clamp( stats_p + g(n) × (potential_p − stats_p), 0, 100 ) )
```

**g(n) = `[0.52, 0.63, 0.74, 0.80, 0.80, …]`** (`web/engine/game.js` `SEASON_GROWTH`)

| 시즌 n | g(n) | 6구단 라인업 OVR 평균 | 최약(라온) | 최강(연화) | 전 시즌 대비 |
|---|---|---|---|---|---|
| 1 | **52%** | **68.7** | 66.6 | 70.3 | — |
| 2 | **63%** | 71.3 | 69.2 | 72.8 | +2.6 |
| 3 | **74%** | 73.6 | 71.6 | 75.0 | +2.3 |
| 4+ | **80% (상한)** | 74.9 | 73.0 | 76.3 | +1.3 → 0 |

(구단별 시즌 1: 연화 70.3 · 가온 69.5 · 해솔 69.3 · 적동 69.2 · 태령 67.6 · 라온 66.6. 라인업 = 선발 6 + 리베로 = 로스터 7명 전부라 로스터 평균과 같다.
측정: `node web/parity.mjs` ①-b 와 같은 정의, `clubTeamState` + 포지션 가중 OVR.)

**왜 v0.1 의 `35 / 48 / 58 / 66 / 72 / 76%` 를 버렸나.** 그 값은 두 가지를 전제로 잡혔다 —
① 승률을 실제 `MatchSimulator` 가 아니라 `sigmoid(0.235 × ΔOVR)` 로 근사했고,
② A.3.5(스카우트된 선수의 원소속 구단 결원)를 **시뮬에 넣지 않았다**(v0.1 이 스스로 D.1 E11·D.2 에 적어 둔 한계다).
둘 다 실제로 구현된 엔진에 초기값을 그대로 얹으니 **시즌 1 정규 승률 59% · 우승률 38%** 가 나왔다 —
목표(40~50% · ≤20%)를 크게 벗어난, "첫 시즌부터 우승하는" 난이도다. `web/season-check.mjs` 로 재캘리브레이션한 것이 위 표다.
**성장 수식은 건드리지 않았다**: g 를 v0.1 값으로 고정하면 옛 표가 그대로 재현된다(g 35% → 65.30 / 58% → 70.31 / 80% → 74.91).

증가폭은 여전히 **체감**한다(+11 → +11 → +6 → 상한). 이유는 A.4 에 있다: 플레이어 로스터의 성장도 체감하므로 사다리가 선형이면 시즌 5 이후 영원히 못 이기거나 영원히 지지 않는다.
다만 v0.1 이 7시즌에 걸쳐 오르던 것이 **시즌 4 에 상한에 닿는다** — 그 결과가 A.4.3 의 열린 이슈다.

**같은 선수, 두 얼굴.** `world.md` 1.2 의 "공개 스카우트 명단" 프레임을 규칙으로 굳힌다.

| 맥락 | 능력치 | 화면 표기 |
|---|---|---|
| 스카우트 대상(플레이어가 뽑는 카드) | `stats` = **신인 초기치** | "원소속: 연화 크레인즈 · 등록: 육성 명단" |
| 리그 상대(원소속 구단 소속으로 출전) | `stats + g × (potential − stats)` = **성장 버전** | 구단 로스터 화면에 실효 스탯 표시 |
| 내 팀에 편입된 뒤 | 육성 졸업 확정치(`PlayerInstance.FinalStats`) | 유니폼 레이어 교체(GDD 9.2) |

서사: **여섯 구단은 매 시즌 유망주를 공개 명단에 올려야 하지만, 명단에 올린 선수를 자기들도 계속 키운다.** 플레이어가 소이든을 스카우트하는 것은 "연화가 아직 꽃피우지 못한 원석"을 데려오는 것이고, 리그에서 마주치는 소이든은 "연화에서 g만큼 자란 소이든"이다. 같은 선수가 양쪽에 존재하는 것이 아니라, **스카우트되는 순간 원소속 구단의 로스터에서 빠진다**(A.3.5).

### A.3.2 AI 구단 라인업

| 항목 | 규칙 |
|---|---|
| 로스터 | `data/players.json` 의 해당 `teamId` **7명 고정**(S1 · OH2 · OP1 · MB2 · L1) |
| 라인업 | 표준 **5-1** 로테이션. `Lineup.Standard51(S, OH1, MB1, OP, OH2, MB2, L)` |
| 교체 | **없음**(7명뿐이라 벤치가 없다). 정식에서 구단당 로스터 12명으로 확장 시 도입 |
| 부상 | **프로토타입 제외.** AI 구단은 부상 없음 |
| 컨디션 | **프로토타입 제외**(`TeamCondition = 1.0`). 정식에서 시즌 서사용 이벤트("연화 에이스 감기몸살")로 도입 검토 |
| 호흡도(케미) | 세터-공격수 기본 50 고정. 정식에서 "명문일수록 높게"(연화 70 / 라온 40) 검토 |

부상·컨디션을 AI 에 넣지 않는 이유: 플레이어는 자기 부상을 통제(육성 정책)할 수 있지만 AI 부상은 순전히 운이고, 그 운이 순위를 바꾸면 사다리의 의미가 흐려진다. **시즌 사다리 = 예측 가능한 벽**이 이 설계의 핵심이다.

`world.md` 2절의 플레이 스타일을 `match-sim.md` 7절 `Tactics` 로 매핑한다. 기본값은 `Q1.2 / O1.0 / B0.7 / D0.5 · ServeAggression 0.5 · Standard`.

### A.3.4 홈 어드밴티지

| 범위 | 값 | 비고 |
|---|---|---|
| 프로토타입 | `Match.HomeCourtLogit = 0.05` | 승률 약 +2.5%p. 존재를 느끼되 순위를 바꾸지 않는 크기 |
| 정식 | 구단별 차등 검토 | 가온 크리스탈 아레나(리그 최대 관중) 0.08, 태령 구름마루(고지대) 0.07, 연화 서원체육관(가장 조용) 0.03 |

시뮬(economy_sim)에서는 승률 근사식에 `home_logit = 0.10`(경기 로짓 0.05 의 경기 단위 환산)을 쓴다.

### A.3.5 스카우트된 선수의 원소속 구단 처리

플레이어가 카드를 스카우트하면 그 선수는 **원소속 구단 로스터에서 빠진다.** 구단은 7명이므로 빈 자리가 생긴다.

| 규칙 | 내용 |
|---|---|
| 결원이 생기는 시점 | **졸업시켜 대표 인스턴스가 된 순간**(엔진 `departedCardIds` = `state.instances` 기준). 뽑아서 보유만 하고 아직 안 키운 카드는 원소속에서 계속 뛴다 |
| 결원 보충 | 그 구단의 **동일 포지션 육성 선수**(제네릭 N 카드, `RandomPlayerGenerator` overall = 해당 구단 평균 **− 4**)로 자동 대체 |
| 기준이 되는 "구단 평균" | **원 로스터 7명의 스탯 평균**으로 고정한다. 결원이 늘어도 대체 선수 강도가 따라 내려가지 않게 하기 위해서다 |
| 표기 | 구단 로스터에 "(육성 선수)" 배지. 리그 순위표 옆 "이적 현황" 탭에서 확인 |
| 밸런스 영향 | 강한 카드를 뽑을수록 그 구단이 약해진다 = **뽑기 성공이 리그에서 두 번 보상된다** |
| 되돌림 | 방출해도 원소속으로 돌아가지 않는다(조각으로 환급) |

**−8 → −4 로 완화한 이유.** v0.1 의 −8 은 이 규칙을 **시뮬에 넣지 않은 채 적은 추정치**였다.
실제로 켜 보니 시즌 1 말에 평균 11장 남짓이 6구단에서 빠져나가고, −8 에서는 AI 평균 OVR 이
**65.3 → 63.6 (−1.7) 으로 시즌 중에 계속 내려갔다**(당시 사다리 g=35% 기준).
사다리는 "예측 가능한 벽"(A.3.2)이어야 하는데, 플레이어가 강해질수록 벽이 같이 무너져 시즌 후반이 급격히 쉬워졌다.

**−4 로 확정한 뒤의 실측**(시즌 1 · n=60 · g=52%):

| 시점 | 6구단 평균 OVR | 최약~최강 | 격차 |
|---|---|---|---|
| 결원 없음(기준) | **68.73** | 66.6~70.3 | 3.7 |
| 시즌 1 개막 (프리시즌 육성 후) | 68.39 | — | — |
| 시즌 1 종료 (졸업 카드 평균 **11.1장** 이탈) | **67.90** | 64.9~70.0 | **5.1** |

시즌 중 하락이 −1.7 에서 **−0.83** 으로 줄었다. "뽑기 성공이 두 번 보상된다"는 서사는 남기되(격차가 3.7 → 5.1 로 벌어진다),
벽이 시즌 중에 붕괴하지는 않는 값이다.

**단위 주의.** −4 는 **스탯 10종의 단순 평균** 공간에서 주는 값이고(`generatePlayer` 의 `overall` 인자),
그것이 포지션 가중 OVR 공간에서는 **−7.4** 로 나타난다(g 35~80% 구간에서 −7.32 ~ −7.53, 구단×선수 42쌍 실측).
`economy_sim.py` 는 OVR 공간에서 돌아가므로 `vacancy_ovr_delta = -7.4` 를 쓴다.

이 규칙은 서사(공개 스카우트 명단 → 실제로 데려간다)와 게임성(SSR 획득의 체감 배증)을 동시에 만든다.
**v0.2 에서 엔진·시뮬 양쪽에 구현됐다**(v0.1 의 "미반영" 단서는 해소됐다).

## A.4 난이도 목표와 사다리의 수학

### A.4.1 목표와 실측 (실제 엔진으로 검증 완료)

**출처: `node web/season-check.mjs` — n=200 · 시즌 1~3 · seed 1.** 시즌 4~5 만 n=60(별도 실행).
자동 플레이어는 "잘하는 유저"에 가깝다 — 최적 정책 + 추천 서포터 + 카드당 재육성 3회 + 구멍 우선 지정 스카우트.

| # | 가설 | 지표 | 목표 | **엔진 실측** | 판정 |
|---|---|---|---|---|---|
| L1 | 시즌 1 은 중위권 | 시즌 1 평균 순위 | 4~5위 | **4.52위** (분포 8/14/12/14/12/20/22%) | ✓ |
| L2 | 첫 승리는 육성 4~8회쯤 | 첫 승리까지 육성 횟수 p50 | 4~8회 | **7회** (p10 4 / p90 11), 매치데이 p50 5 | ✓ |
| L3 | 시즌 1 우승은 예외적 | 시즌 1 우승률 | ≤ 20% | **16.5%** | ✓ |
| L4 | 시즌 2~3 이 우승 창 | 첫 우승 시즌 분포 | S2+S3 ≥ 50% | **S2 37% + S3 18% = 54.5%** | ✓ |

검증 하네스가 "잘하는 유저"를 가정하므로 그 표본에서 16.5% 는 평균 유저 기준으로는 더 낮다고 보는 것이 타당하다.
(평균 유저 표본은 아직 없다 — D.2 열린 이슈.)

### A.4.2 왜 사다리가 필요한가 — 수식

플레이어 라인업 OVR 을 `P(n)`, AI 구단 평균을 `C(n) = f(g(n))` 라 하자. 승률은 밸런스 리포트 9절(팀 overall 57/62/67/72/77 → 8.5/23.6/49.5/76.3/90.8%)을 로지스틱으로 회귀한 근사식이다.

```
승률(경기) ≈ sigmoid( 0.235 × (P − C) + 홈보정 )
```

`0.235` 는 **OVR 1 차이 ≈ 승률 5.8%p**(동급 근방)를 뜻한다. OVR 5 차이면 76%, 10 차이면 91%.

플레이어의 성장은 **로스터 7슬롯의 최댓값 갱신**이라 강하게 체감한다:

```
P(n) ≈ (1/7) Σ_slot  max( 그 포지션에서 보유한 인스턴스들의 OVR ,  연습생 46.0 )
```

연습생 라인업 OVR 은 실측 **시즌 1 = 46.00**, 시즌당 +0.83, 고원 49.7 이다
(`fillerOverall` 44 + 시즌당 1, 상한 48 을 포지션 가중 OVR 로 환산한 값).

시즌 1 개막에 4개 슬롯이 연습생이므로 **첫 몇 회 육성이 슬롯당 +15~20 OVR** 을 준다(라인업 OVR 56.1 → 67.9).
그다음부터는 이미 R 카드가 앉은 자리를 SR 로 바꾸는 +9 남짓뿐이고, 그마저 카드 운에 걸린다.

**아래는 전부 엔진 실측**(개막 = 프리시즌 육성 후 매치데이 1 직전 / 중반 = 매치데이 7 / 종료 = 결산 시점).
시즌 1~3 은 n=200, 시즌 4~5 는 n=60.

| 시즌 | 내 라인업 P (개막→종료) | AI 평균 C | 개막 시점 격차 | 종료 시점 격차 |
|---|---|---|---|---|
| 1 | 56.1 → **69.8** (+13.7) | 68.7 | **−12.6** | **+1.1** |
| 2 | 71.1 → **73.1** (+2.0) | 71.3 | −0.2 | +1.8 |
| 3 | 73.9 → **75.2** (+1.3) | 73.6 | +0.3 | +1.6 |
| 4 | 75.5 → **76.4** (+0.9) | 74.9 (상한) | +0.6 | +1.5 |
| 5 | 77.1 → **77.7** (+0.6) | 74.9 (상한) | +2.2 | **+2.8** |

시즌 간 증분으로 다시 보면:

| 전이 | 플레이어 ΔP (종료→종료) | AI ΔC | 종료 시점 격차 변화 |
|---|---|---|---|
| 1→2 | 69.8 → 73.1 = **+3.3** | 68.7 → 71.3 = +2.6 | +1.1 → **+1.8** |
| 2→3 | 73.1 → 75.2 = **+2.1** | 71.3 → 73.6 = +2.3 | +1.8 → **+1.6** |
| 3→4 | 75.2 → 76.4 = **+1.2** | 73.6 → 74.9 = +1.3 | +1.6 → **+1.5** |
| 4→5 | 76.4 → 77.7 = **+1.3** | 74.9 → 74.9 = **0** | +1.5 → **+2.8** |

**설계 의도는 시즌 3까지 성립한다.** ΔP 가 +3.3 → +2.1 → +1.2 로 줄고 ΔC 가 +2.6 → +2.3 → +1.3 으로 따라 줄어,
격차가 +1.1 ~ +1.8 의 좁은 띠에 머문다 — "우승은 하지만 매 시즌 싸워야 하는" 상태다.

**깨지는 것은 시즌 4 부터다.** g 가 상한 80% 에 닿아 ΔC 가 0 이 되는데 ΔP 는 아직 +1.3 이라, 격차가 +1.5 → +2.8 로 벌어진다.
v0.1 은 g 를 7시즌에 걸쳐 올려 이 지점을 시즌 6~7 로 미뤘지만, v0.2 의 사다리는 시즌 4 에 상한에 닿는다(A.4.3).

> v0.1 의 이 표는 승률 로지스틱 근사 위의 **추정치**였고(P 55.0 → 67.5 등), 위 값과는 다르다.
> 특히 v0.1 이 예상한 "격차 +2.9~+3.3 고원"은 실제로는 시즌 3까지 **+1.1~+1.8** 로 더 팽팽하다.

### A.4.3 사다리가 만드는 압박 — 그리고 시즌 4 이후의 열린 이슈

시즌 4 이후 g 가 상한(80%)에 닿으면 AI 는 더 이상 강해지지 않는다. 그때부터는 **로스터를 안 키우면 순위가 유지된다**. 이것은 의도된 종착점이다 — 무한 사다리는 F2P 유저를 이탈시킨다. 이후의 도전 축은 리그가 아니라 **PvP 랭킹·픽업 카드·완성도 갱신**으로 넘긴다(GDD 6·8절).

**다만 v0.2 의 사다리는 그 종착점에 시즌 4 에 닿는다** — v0.1 이 상정한 시즌 6~7 보다 두세 시즌 이르다.
g 초기값을 올린 대가이고, 결과는 A.4.1 L5 의 미충족이다:

| 시즌 | 3 | 4 | 5 |
|---|---|---|---|
| g | 74% | **80% (상한)** | 80% |
| AI 평균 OVR | 73.6 | 74.9 | 74.9 |
| 내 라인업 OVR (종료) | 75.2 | 76.4 | 77.7 |
| **우승률 (실측 n=60)** | 50% | **68%** | **73%** |

목표는 "단조 증가가 아닌 고원"(v0.1 은 S3 48% → S4 50% → S5 46% 를 예상했다)인데, 실측은 계속 오른다.
원인은 위 표 그대로다 — **g 가 멈춘 뒤에도 내 라인업 OVR 은 76.4 → 77.7 로 계속 오른다.**

**여기서는 고치지 않았다.** 해소하려면 둘 중 하나가 필요한데 어느 쪽이든 이 절과 A.3.1 의 기획 결정을 바꾸는 일이다:

| 안 | 내용 | 대가 |
|---|---|---|
| (a) 상한을 0.88 정도로 올린다 | 사다리를 시즌 6~7 까지 늘린다 | 이 절의 "의도된 종착점" 서사를 포기. 잠재력 88% 면 AI 가 사실상 완성형이라 카드 개성이 옅어진다 |
| (b) AI 구단 로스터를 7 → 10~12명으로 확장 | 벤치·교체가 생겨 상한 없이도 강해진다 | `data/players.json` 42명 확장이 선행. A.3.2 "교체 없음" 결정을 뒤집는다 |

**검증 대상인 시즌 1~3 목표 7개는 전부 충족한다**(A.4.1). 시즌 4 이후는 프로토타입의 검증 범위 밖이므로
"알고 있는 미해결"로 남긴다(D.2).

### B.1.2 왜 골드를 새로 두는가

프로토타입에는 티켓과 조각뿐이라 **"돈이 있는데 쓸 데가 없다/티켓이 없어 아무것도 못 한다"의 두 상태만** 존재했다. 골드는 세 가지를 한다.

1. **포지션 지정 스카우트의 가격표.** 티켓 1 + 골드 1,200. 티켓만으로 지정할 수 있으면 일반 스카우트를 아무도 안 쓴다.
2. **경기의 즉시 보상.** 티켓은 12조각(경기 2~4회)을 모아야 나오지만 골드는 매 경기 들어온다 — 패배해도 손에 뭔가 남는다(프로토타입 피드백의 "패배 조각" 을 계승·확장).
3. **장비·굿즈(GDD 7절)의 화폐.** 정식에서 로스터 강화의 비가챠 축.

엔진 실측 3시즌 뒤 골드 잔액 **10,564** — 소비처가 포지션 지정뿐이라 아직 남는다(시즌 1 말 9,344 / 시즌 2 말 9,477 / 시즌 3 말 10,564 로 계속 쌓인다). 정식의 장비·보관함 확장이 이 잉여를 흡수해야 한다(D.2 열린 이슈).

**확률을 R 80 / SR 17 / SSR 3% 에서 바꾸지 않는 이유.** `prototype-play.md` 6.4 #2 는 "R 80% 가 로스터 성장을 R 카드에 묶는다(3시드 24회에서 SSR 0장, 첫 SSR 기대 33회)"고 지적했다. 확률을 올리는 대신 **천장 + 포지션 지정 + 조각 가치**로 풀었다. 이유:

- 확률 자체를 올리면(예: SSR 5%) 표기 확률이 경쟁작 대비 높아 보이지만 **분산은 그대로**라 "60회 뽑았는데 없다"는 유저는 여전히 생긴다. 천장은 분산의 꼬리를 자른다.
- R 카드가 무가치한 것이 근본 문제였는데, 이는 **중복 R 이 곧바로 한계돌파 1단계**가 되는 것과 **포지션 지정으로 R 을 원하는 자리에 배치**하는 것으로 해소된다(B.4). 실측 3시즌 누적 한계돌파 26.0단계.
- 국내 확률형 아이템 표시 의무상 확률과 천장은 모두 공개해야 하므로, "천장 있는 3%" 가 "천장 없는 5%" 보다 설명하기 쉽고 유저 신뢰도 높다.

### B.2.2 천장 규칙

```
매 뽑기마다:
  pitySR  += 1
  pitySSR += 1
  if pitySSR >= 60:  결과 = SSR           # 하드 천장
  elif pitySR >= 10: 결과 = SR 또는 SSR    # SSR 비중 = 3/(3+17) = 15%
  else:              결과 = 기본 확률표
  결과가 SR 이상이면 pitySR = 0
  결과가 SSR      이면 pitySSR = 0
```

| 규칙 | 실효 등급 확률 | SSR 간격 평균 | SSR 간격 p50 / p90 / 최대 | SR+ 간격 p90 / 최대 |
|---|---|---|---|---|
| 천장 없음 | R 79.9 / SR 17.1 / SSR 3.09% | 32.4 | 23 / 73 / **260** | 11 / 45 |
| SR 10 만 | R 77.5 / SR 19.1 / SSR 3.43% | 29.1 | 21 / 65 / **236** | 10 / 10 |
| **SR 10 + SSR 60 (채택)** | **R 77.2 / SR 18.9 / SSR 3.87%** | **25.9** | 21 / 60 / **60** | 10 / 10 |
| SR 10 + SSR 50 (대안) | R 77.1 / SR 18.8 / SSR 4.10% | 24.4 | 21 / 50 / 50 | 10 / 10 |

(120,000회 뽑기, `economy_sim.py --only new`)

**천장 카운터는 일반과 포지션 지정이 공유한다.** 이유: 분리하면 "천장 직전에는 포지션 지정을 쓰면 손해"라는 역-최적화가 생겨 유저가 원하는 포지션을 못 뽑게 된다. 픽업만 별도 카운터를 두는 것은 업계 표준이고, 픽업 종료 시 카운터 이월 여부는 정식 정책으로 미룬다(D.2).

### B.2.4 중복 처리와 한계돌파

**구현된 규칙 (v0.2):**

```
중복 카드 획득 → 그 카드의 한계돌파 +1 단계 (즉시, 최대 5단계 = 전 스탯 potential +15)
조각 12개    → 스카우트 티켓 1        (조각은 경기 보상·방출에서만 나온다)
```

**v0.1 의 "중복 → 희귀도 조각 10 → 30개마다 1단계"는 채택하지 않았다.** 두 가지 이유다.

1. 엔진의 조각 풀은 **하나**다. 희귀도별로 나뉘지 않아 "R 조각은 R 카드만 돌파" 규칙이 성립하지 않고, 5:1 상위 변환도 없다.
2. 조각 풀이 하나인 채로 중복에 조각 10 을 주면 **조각이 곧 티켓**이 된다(10 조각 = 티켓 0.83).
   즉 뽑기 1회가 뽑기 0.83회를 재생산하는 되먹임이 생겨, 실측에서 **시즌 2 스카우트가 63회**까지 폭주했다.
   중복이 이미 한계돌파 1단계를 통째로 주고 있으므로 조각까지 얹을 이유도 없다.

- **한계돌파는 카드 단위**(인스턴스가 아님). 돌파 후에는 **재육성해야 반영된다** — "상한이 올랐으니 다시 키운다"가 `training-mode.md` 8.6절 재육성 루프의 동력이다.
- 중복은 희귀도와 무관하게 같은 값(1단계)이다. R 중복도 R 카드를, SSR 중복도 SSR 카드를 각각 돌파시킨다.
- 한계돌파 5단계의 OVR 효과(`economy_sim.py` 회귀 모델 추정): R OH 59.9 → **67.2**, SR OH 68.2 → **75.2**, SSR OH 77.6 → **82.6**. 즉 **풀돌 R ≈ 무돌 SR, 풀돌 SR ≈ 무돌 SSR** — training-mode 8.2 의 "한계돌파가 쌓이면 SR 도 A 에 닿는다"와 정합한다.

### B.2.5 42명 풀의 "이미 가진 카드" 문제

시즌 3 까지 누적 스카우트 **52.4회에 중복 28.4회(54%)** (엔진 실측 n=200). 42장 풀에서 이는 구조적이다. 세 겹으로 대응한다.

| 대응 | 내용 | 효과 |
|---|---|---|
| ① 중복의 가치 보장 | 중복 = **한계돌파 1단계 즉시** (3시즌 누적 26.0단계) | 중복이 "꽝"이 아니라 **한계돌파 진척**이 된다 |
| ② 포지션 지정으로 풀 축소 | 지정 시 풀이 7~9장으로 줄어 원하는 자리를 채운다 | 초반 구멍 메우기 가속(B.4) |
| ③ 풀 확장 계획 | 런칭 42명 → **월 2~4명 신규**(GDD 9.6). 12개월 뒤 66~90명 | 중복률 하락 + 픽업 소재 공급 |

**풀 확장 시 확률 유지 규칙**: 신규 카드는 등급 정원에 더해지되 **등급별 총 확률(80/17/3)은 고정**하고 등급 내 개별 확률이 얇아진다. 즉 SSR 이 10 → 15명이 되면 특정 SSR 1명을 뽑을 확률은 0.30% → 0.20%. 이때 **픽업(정식)** 이 "원하는 1명"의 유일한 경로가 되므로, 픽업 없는 프로토타입 단계에서는 풀을 42명으로 고정한다.

승률 20%p 차이로 증폭된다. 상수를 하나씩 바꿔 본 분해(파이썬 n=300):

### B.3.3 희귀도 획득과 첫 SSR

엔진 실측(n=200).

| 지표 | 값 |
|---|---|
| 첫 SSR 획득 누적 확률 | **시즌 1 52% · 시즌 2 72% · 시즌 3 84%** |
| 첫 SSR 까지 스카우트 횟수 | p10 **1** / p50 **7** / p90 **30** (3시즌 안에 얻은 167/200명 기준) |
| 시즌 1 SSR 기대 신규 획득 | 0.66장 · SR 2.8장 |
| 3시즌 누적 | 스카우트 52.4회 · 신규 R 14.9 / SR 7.3 / SSR 1.82 |

**목표(시즌 1 말~시즌 2 초)에 대한 판정: ✓.** v0.1 의 근사 추정(시즌 1 39%)보다 훨씬 이르다 —
**시즌 1 안에 52%, 시즌 2 까지 72%** 가 첫 SSR 을 받는다.

**왜 이렇게 빨라졌나 — 포지션 지정의 부수 효과.** p10 이 1 회인 것은 우연이 아니다.
엔진의 지정 스카우트는 **등급을 먼저 뽑고 그 등급에서 해당 포지션 카드를 고르는데, 그 포지션에 그 등급 카드가 없으면
같은 포지션의 아무 등급으로 폴백**한다. 세터 풀은 SR 4 + SSR 2 로 **R 이 한 장도 없어서**, 세터를 지정해 R 이 나오면
폴백이 SR/SSR 중 하나를 준다. 자동 플레이어는 첫 스카우트를 빈 자리(세터)에 쓰므로 **첫 뽑기가 사실상 SR+ 확정**이다.

> 이 폴백은 v0.1 B.4 ③ 이 적어 둔 "**N 무명 신인** 폴백"과 **다르다**. 엔진에는 N 무명 신인 카드가 없다(카드 풀은 `data/players.json` 42장뿐).
> 결과적으로 "구멍은 반드시 메워진다"는 목적은 달성하지만, "정식 카드를 대체하지는 않는다"는 단서는 성립하지 않는다 — 오히려 상위 카드가 나온다. 열린 이슈(D.2).

**SSR 하드 천장 60 은 여전히 사실상 장식이다.** 3시즌 누적 스카우트가 52.4회라 60회에 거의 닿지 않는다.
다만 첫 SSR 시점이 목표를 이미 만족하므로 **천장 60 을 유지한다**(v0.1 의 "60 → 40" 검토는 근거였던 39% 가 실측 52% 로 바뀌어 불필요해졌다).
`SSR 천장 40` 은 정식에서 미션 수입이 붙어 뽑기 횟수가 늘 때 다시 볼 문제로 남긴다(D.2).

### B.3.4 스태미나로 정해지는 육성 횟수

| 항목 | 값 |

| 육성 1회 | 스태미나 30 |
| 상한 / 회복 | 120 / 6분당 1 (하루 240) |

### B.3.5 시나리오 비교 (근사 모델 — **상대 비교 전용**)

**중요한 발견 — 정식 미션이 사다리를 깬다.** 일일 티켓 1 + 주간 3 을 얹으면 시즌당 스카우트가 12 → 33회로 2.7배가 되어

## B.4 프로토타입에서 나온 문제에 대한 답

`prototype-play.md` 6.4절의 세 가지 문제를 새 설계가 어떻게 푸는지 대조한다.
**대조군("현행 프로토타입 규칙")은 엔진에 존재하지 않으므로 근사 모델 값이고, "신규 설계" 열은 엔진 실측이다.**
두 열의 출처가 다르니 절대 비교가 아니라 각 열 안의 추세로 읽어야 한다 — 열 제목에 출처를 적었다.

| 지표 | 현행 프로토타입 규칙 *(근사)* | **신규 설계 — 엔진 실측** |

기여 분해: **천장(SR 10회)이 SR 공급을 2배로 늘렸고**, 이것이 라인업 OVR 의 주 동력이다.

3시즌 중복 28.4회가 거의 그대로 26.0단계가 된다(카드당 상한 5단계에 걸린 몫이 차이).

| 지표 | 현행(일반만) *(근사)* | 신규 − 지정 미사용 *(근사)* | **신규(지정 사용) — 엔진 실측** |
|---|---|---|---|
| 라인업 7슬롯 전원 정식 카드 도달 (누적 매치데이 p50 / p90) | 28 / 42 | 21 / 42 | **시즌 1 안에 100%** (충원 시즌 p50 1.0) |
| 3시즌 내 미도달 | 44% | 20% | **0%** |
| 시즌 1 중반(매치데이 7) 연습생 슬롯 | 2.0 | 1.7 | **0.3** |
| 3시즌 뒤 잔여 구멍 포지션 | S 0.32 · OP 0.16 · MB 0.01 · L 0.01 | S 0.15 · OP 0.05 | **전부 0.00** |
| 시즌 1 승률 | 16% *(근사)* | 20% *(근사)* | **45%** *(엔진)* |

프로토타입 관찰(시드 3 이 MB 4 / OH 2 로 뽑혀 S·OP·L 자리에 8회차까지 연습생)이 정확히 재현된다: 지정 없이 일반만 쓰면 **S(단 6장, 그중 R 0장)와 OP(단 6장)** 에 구멍이 남는다. S 는 R 등급 카드가 아예 없어(런칭 42명 구성상 S 는 SR 4 · SSR 2) 일반 뽑기로는 17+3=20% 확률의 SR/SSR 을 기다려야 한다.

**포지션 지정 스카우트가 이 구조적 구멍을 직접 겨냥한다.** 지정 시 S 풀은 6장(SR 4 + SSR 2)이라 **무조건 SR 이상이 나온다**
— 등급을 먼저 뽑고 R 이 나오면 그 포지션의 아무 등급으로 폴백하는데, 세터에는 R 이 없기 때문이다(B.3.3).
자동 플레이어가 첫 티켓을 세터에 쓰므로 "세터가 연습생이라 공격 조립이 무너진다"는 최악의 시작은 실측에서 발생하지 않는다
(시즌 1 개막 라인업 OVR **56.1**, 매치데이 7 에 연습생 슬롯 0.3).

> **v0.1 의 두 가지 단서는 v0.2 에서 성립하지 않는다.**
> ① **튜토리얼 SR 세터 확정 지급은 구현되지 않았다** — 엔진 `createGame` 은 카드 0장으로 시작한다.
> 위 개막 OVR 56.1 은 세터를 **뽑아서** 확보한 뒤의 값이다.
> ② **N 무명 신인 폴백도 없다** — 카드 풀에 N 카드가 없어, 폴백은 같은 포지션의 상위 등급으로 간다.
> 결과적으로 "구멍은 메워진다"는 목표는 초과 달성하지만 "정식 카드를 대체하지는 않는다"는 제동 장치는 없는 셈이다(D.2).

> **v0.2 주 — 실제로 구현된 곳은 여기가 아니다.** 리그·경제 계층은 브라우저 플레이용 자바스크립트

## C.4 결정성 (시드) 요구

`match-sim.md` 10절의 결정성 요구를 리그 계층으로 확장한다. **같은 `LeagueState` + 같은 입력 = 같은 결과**여야 서버 재검증과 리플레이가 성립한다.

| 대상 | 시드 파생 | 비고 |
|---|---|---|
| 시즌 일정 셔플 | `H(accountSeed, seasonNumber, "schedule")` | 시즌마다 대진 순서가 다르되 재현 가능 |
| 매치데이 경기 | `H(seasonSeed, matchDay, fixtureIndex)` | 경기 하나의 시드가 다른 경기와 독립 → 병렬 시뮬 가능 |
| 포스트시즌 경기 | `H(seasonSeed, "po", round, game)` | |
| 스카우트 1회 | `H(accountSeed, "scout", pullIndex)` | `pullIndex` 는 계정 통산 뽑기 횟수 — **재시도로 결과를 바꿀 수 없다** |
| 육성 세션 | 기존 `TrainingSession` 시드 규칙 유지 | `H(accountSeed, "train", runIndex)` |
| 연습생 세대 | `H(accountSeed, "filler", seasonNumber)` | |

- 해시 `H` 는 `DeterministicRandom` 의 SplitMix64 확장을 그대로 쓴다(정수 연산만, 플랫폼 무관).
- **난수 소비량을 결과에 기록**한다(`MatchResult.RandomDraws` 와 동일한 패턴) — 서버·클라 불일치 조기 발견용.
- 부동소수점 주의사항은 `match-sim.md` 10절 그대로. 리그 계층은 **정수·비교 연산만** 쓰도록 설계했다(승점·타이브레이크의 세트 득실률만 double 이며, 이는 비교에만 쓰이고 누적되지 않는다).

## C.5 기존 코드와의 접점

| 기존 | 접점 | 필요한 변경 |
|---|---|---|
| `VolleySim.Core.MatchSimulator.Simulate(home, away, hT, aT, seed, cfg, collectEvents)` | 매치데이 경기·포스트시즌 경기 | **변경 없음.** 리그는 이 API 만 호출 |

| `VolleySim.Core.Data.JsonDataLoader.BuildTeamState` | AI 구단 TeamState 생성 | 성장 적용 후 호출. `ClubStrengthLadder.Grow` 가 `Player.Clone()` 후 스탯만 덮어쓴다 |

| `VolleySim.Training.PlayerInstance.ToPlayer(teamId)` | 로스터 → 경기용 Player | 변경 없음 |
| `VolleySim.Training.PlayerInstance.ToSupporter()` | 서포터 편성 | 변경 없음 |
| `VolleySim.Play.GameState` | **`LeagueState` 로 흡수.** `Tickets`/`Fragments`/`OwnedCards`/`Instances`/`Fillers`/`Lineup*` 를 이관 | `GameState.Version` 마이그레이션 1 → 2. `ScoutR/SR/SSR` 상수는 `ScoutConfig` 로 이동 |
| `VolleySim.Play.Game.Scout()` | `ScoutService.Draw` 로 대체 | 현재 구현은 천장·포지션 지정·조각이 없고 중복이 즉시 한계돌파다(B.4 대조군). **규칙 교체 필요** |

**가장 작은 첫 걸음**: `Game.ClubTeamState` 의 `OpponentGrowth` 를 `SeasonNumber` 에서 파생시키고(`GrowthLadder[n-1]`), `Game.Scout` 에 천장·포지션 지정을 넣는 것. 이 둘만으로 콘솔에서 사다리와 스카우트 개선을 체감할 수 있고, 리그 일정·순위는 그다음이다.
