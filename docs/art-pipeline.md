## 1. 프롬프트 팩 (`tools/art-prompts.mjs`)

`docs/art-style-guide.md` 6절의 템플릿은 `{hairStyle}` 같은 빈 슬롯이 뚫려 있고, `data/players.json` 의 외형 값은
`"롱 하이 포니테일"`·`"플래티넘 블론드"` 같은 한국어다. 이 둘을 잇는 것이 이 스크립트다.

```bash
node tools/art-prompts.mjs           # 42명분 생성 + 커버리지 리포트
node tools/art-prompts.mjs --check   # 파일을 쓰지 않고 검사만 (CI 게이트)
node tools/art-prompts.mjs --id p001 # 한 명만 표준출력으로
```

한 명당 나오는 것: **카드(태그형 + 자연어형) · 스탠딩 · SD 토큰 · 표정 4종 · 네거티브 2종**(카드/스탠딩 공용, 토큰 전용).
공용 고정 파라미터는 `_params.txt`, 전체 목록은 `_index.md`.

### 1.0 태그형과 자연어형

같은 매핑표에서 **두 가지 형태**를 뽑는다. 어휘를 두 벌 관리하지 않으려고 자연어는 태그에서 기계적으로 만든다.

| 형태 | 대상 | 예 |
|---|---|---|
| 태그형 | 로컬 SD · 애니메 SDXL(Danbooru 태그 학습) | `high ponytail, long hair, platinum blonde hair, purple eyes, tareme` |
| 자연어형 | Higgsfield(Soul·Seedream·Flux) · Midjourney 등 호스팅 모델 | `A tall, slim and athletic young woman with fair skin, long platinum blonde hair worn in a high ponytail and gentle, softly drooping purple eyes.` |

변환 규칙에서 주의한 것: 질감(straight/wavy/curly/layered)은 `with wavy hair` 가 아니라 **형용사로 앞에** 붙이고,
자른 머리(bob/pixie/hime/cropped)에는 길이 수식을 붙이지 않으며(`in a cropped hair` 방지),
눈 색과 눈매는 **한 덩어리**로 만든다(둘 다 `eyes` 로 끝나면 문장이 깨진다).
체형은 태그(`tall, slim athletic build`)가 명사구라 문장용 형용사구를 따로 둔다(`tall, slim and athletic`).
42종 헤어 전부 출력해 눈으로 확인했다.

### 1.1 어휘는 닫혀 있다

| 항목 | 값 개수 | 매핑 |
|---|---|---|
| 헤어스타일 | 42 | 42 ✅ |
| 헤어 컬러 | 24 | 24 ✅ |
| 눈 색 | 20 | 20 ✅ |
| 체형 | 15 | 15 ✅ |

런칭 42명과 **신인 세대 생성기**(`web/engine/rookies.js`)가 같은 목록에서 값을 뽑기 때문에,
이 표가 가득 차 있으면 앞으로 생길 카드도 전부 프롬프트를 만들 수 있다.
매핑에 없는 값이 하나라도 들어오면 스크립트가 **에러로 죽는다** — 조용히 빈 슬롯으로 넘어가지 않는다.

### 1.2 데이터에 없어 생성기가 배정하는 값

`art-style-guide` 는 요구하는데 `data/players.json` 에는 필드가 없는 것이 둘 있다. 생성기가 **결정적으로** 배정하고,
그 사실을 각 프롬프트 파일 머리말에 적는다.

| 값 | 규칙 | 실측 |
|---|---|---|
| 피부 3톤(2.7) | id 정렬 순서로 주기 배정 후, 단일 톤 구단이 없게 보정 | A/B/C = 26/12/4 (62/29/10%, 권장 60/30/10) · 구단별 최소 2톤 |
| 눈매(2.5·6.2) | id 순서 + 포지션으로 tsurime/neutral/tareme 순환 | — |

정식으로 하려면 `data/players.json` 스키마에 `skinTone`·`eyeShape` 를 넣고 생성기는 그것을 읽게 바꾸면 된다(11절).

### 1.3 프롬프트 조립 규칙

- **체형은 데이터의 `bodyType` 이 담당하고, 포지션은 그 포지션에서만 나오는 특징만 얹는다**(S `long fingers`,
  OP `long legs, broad shoulders`, MB `long arms`). 그러지 않으면 `장신 슬림 애슬레틱` + `athletic build` 처럼 같은 말이 겹쳐
  태그가 흐려진다.
- 태그 나열은 중복 제거를 거친다.
- **토큰(6.7)은 공용 네거티브를 쓰면 안 된다** — 공용 쪽에 `chibi` 가 들어 있어 서로 싸운다. 전용 네거티브를 따로 낸다.
- 리베로는 구단 대비색 유니폼으로 조립한다(5.4). 카드만 봐도 리베로여야 한다.
- **작가명·작품명·스튜디오명을 넣지 않는다.**

## 2. 파일을 넣는 곳 (`art/04_export/`)

```
art/04_export/{pid}/
  {pid}_card.webp      3:4   (권장 2048×2732)   카드 일러스트
  {pid}_thumb.webp     1:1   (권장 512×512)     원형 초상 — 로스터·라인업·육성 목록
  {pid}_meta.json                                얼굴 좌표 등. 없어도 동작한다
```

- `webp` 가 `png` 보다 우선한다(같은 화질에 30~40% 크기). `png`·`jpg` 도 읽는다.
- **비율만 검사하고 해상도는 강제하지 않는다.** 작업 중에 낮은 해상도로 먼저 확인하는 편이 낫기 때문이다.
- 폴더 이름과 파일 접두사는 `data/players.json` 의 `id` 와 같아야 한다(`p001`…). 신인 세대 카드는
  런타임 생성이라 아트를 붙일 수 없다 — 항상 SVG 플레이스홀더다(11절 열린 이슈).

원본(`02_gen`)·작업 파일(`03_work`)·LoRA 데이터셋(`06_lora`)은 용량이 커서 저장소에 넣지 않는다.
**`04_export` 만 커밋한다**(art-style-guide 4.9).

```bash
node web/art-pack.mjs        # 지금 무엇이 들어와 있는지 · 비율이 맞는지 · 합계 용량
```

## 3. 게임에 들어가는 방식

빌드가 `04_export` 를 훑어 **data: URI 로 HTML 안에 인라인**한다(`window.BLOOM_ART`).

왜 인라인인가: 산출물이 단일 HTML 한 장이고, 아티팩트로 게시하면 외부 이미지가 CSP 로 막힌다.
휴대폰에 파일 하나만 건네도 그림이 보여야 한다.

```bash
node web/build.mjs
# web/dist/bloom.html  484KB  (아트 없음 — SVG 플레이스홀더)
# web/dist/bloom.html  6.2MB  (아트 12명 · 5.71MB)          ← 그림이 들어오면
```

**용량 예산 11MB**(`ART_BUDGET_MB`). 아티팩트 상한 16MB 에 여유를 둔 값이고, 넘으면 빌드가 경고한다.
42명 전원의 카드+썸네일을 넣을 것이므로 **카드 1장을 200KB 안쪽으로** 잡아야 한다(webp 품질 80 · 긴 변 1400px 정도).
원본 2048×2732 PNG 는 저장소·Unity 용이고, 웹 프로토타입에는 축소본을 넣는다.

화면 쪽은 `portraitSvg()` / `cardArtSvg()` 가 아트를 먼저 찾고 없으면 SVG 로 떨어진다. 둘은 같은 상자를 쓴다.

### 5.1 원본 → 규격 변환 (`tools/art-import.mjs`)

생성 도구가 내주는 비율(2:3 등)과 용량(2MB)은 카드 규격이 아니다. 이 스크립트가 4.2·4.3 규칙대로 잘라 넣는다.

```bash
node tools/art-import.mjs p001 원본.png --face 470,310,180   # 얼굴 중심 x,y 와 얼굴 높이(원본 픽셀)
node tools/art-import.mjs p001 원본.png --face 470,310,180 --dry   # 계산만 보고 파일은 안 씀
```

- 카드는 3:4 로, **얼굴 중심이 세로 30% 에 오도록** 맞추고 원본을 벗어나면 경계로 민다.
- 썸네일은 한 변 = 2.2 × 얼굴 높이, 중심 = (cx, cy + 0.15 × 얼굴 높이).
- WebP 로 인코딩하며 **카드 200KB · 썸네일 60KB** 예산에 들 때까지 품질을 낮춘다.
- 카드 좌표계로 환산한 얼굴 위치를 `{pid}_meta.json` 에 남긴다.
- 이 환경에는 ImageMagick·Pillow·sharp 가 없어 **이미 있는 Chromium 의 캔버스**로 처리한다. 새 의존성이 없다.

### 5.2 히어로 시험 1호 (p001 서하율) — 결과

첫 실물 카드를 넣어 보고 얻은 것. **프롬프트를 고친 근거가 전부 여기서 나왔다.**

맞은 것: 헤어(플래티넘 블론드 롱 하이 포니테일)·눈(바이올렛)·유니폼 색(t01 바이올렛+사이언)·빈 유니폼(5.2)·
무릎보호대·양말·배구화·스파이크 포즈·로우앵글 포어쇼트닝·체육관과 네트·SSR 조명. **스타일 자체는 목표에 근접했다.**

고쳐야 하는 것:

| # | 문제 | 근거 | 대응 |
|---|---|---|---|
| 1 | 원본이 2:3(1024×1536) | 규격 3:4 | 생성 단계에서 3:4 로 뽑는다. 지금은 하단 171px 을 잘라 맞췄다 |
| 2 | **카드 96px 에서 얼굴이 안 읽힌다** | 얼굴이 (46%, 23%) 에 있고 머리 높이가 프레임의 13% — 4.2 는 (50%, 30%)±(6,5) 에 머리 높이 18~23% 를 요구 | 자연어 프롬프트에 프레이밍 문장을 명시 |
| 3 | 프레임 중앙이 엉덩이·허벅지 | 1.4 "엉덩이·가슴 중심 프레이밍 금지" | 위와 같음 + 네거티브에 `ass focus, hip focus` |
| 4 | 쇼츠가 짧고 밀착 | 1.4 "밑단 = 사타구니→무릎의 1/3 이상 아래", "밀착 부위 형태 강조" 금지 | 포지티브에 쇼츠 길이·루즈핏 문장, 네거티브에 `skin tight shorts, short shorts` |
| 5 | 가슴 과장 | 1.4 "가슴 과장" 금지 | 포지티브 `loose fit jersey, modest sportswear` |
| 6 | 허벅지에 흐르는 땀 | 1.4 "땀은 얼굴·목·팔에 소량 방울로만" | 네거티브 `wet thighs, sweat on thighs` |
| 7 | **공이 파랑/노랑/흰 18패널** | 9.x "실제 배구공 브랜드 색 배열 금지" · 4.8 공식구는 흰 `#F4F5F8` + 민트 `#3EC1B3` + 코랄 `#FF6B57` | 자연어에 공 색 문장 추가, 네거티브 `branded volleyball` |
| 8 | 원본 2MB | 예산 카드 200KB | `art-import.mjs` 가 WebP 98KB 로 변환(42명 ≈ 5.3MB, 예산 11MB 안) |

**호스팅 모델은 네거티브를 안 받을 수 있어 포지티브가 방어선이다** — 그래서 1.4 의 금지선을 포지티브 문장으로도 못박았다.

### 5.3 히어로 시험 2호 — Higgsfield MCP 로 직접 생성

카탈로그에 애니메 전용 모델이 없어 **프롬프트 준수력**으로 골랐다.

**프롬프트로 고쳐진 것** (1호의 8건 중 6건):

| 1호 문제 | 2호 결과 |

| 공이 실제 브랜드 색 배열 | ✅ 흰+민트+코랄로 나온다 |
| 비율 2:3 | ✅ 3:4(1792×2400) |

**2호에서 새로 나온 것과 대응:**

- **한 장에 "SUPER SPIKE" 글자가 박혔다.** 모델이 "trading card" 라는 말에 제목을 얹으려 한다.
  → 텍스트 금지를 **맨 앞 문장**으로 올렸다.
- **두 장에서 배꼽이 드러났다**(1.4 위반). → "밑단이 쇼츠에 들어가 있고 배는 완전히 가려진다"를 명시.
- **신발에 브랜드 마크 같은 무늬.** → `plain white volleyball shoes with no markings`.

**프롬프트로 안 고쳐지는 것 하나 — 얼굴 크기.**

6장 전부 머리가 프레임의 **10~16%** 로 나왔다. 4.2 규격은 18~23% 다.
"머리가 화면 높이의 1/5", "head-and-torso hero shot", "전신을 잡지 마라"를 다 넣어도 모델은 전신을 그린다.
크레딧을 더 쓰며 프롬프트를 다투는 대신 **크롭으로 맞춘다**:

```bash
node tools/art-import.mjs p001 원본.png --face 700,490,240 --headfrac 0.20
```

`--headfrac` 는 "카드 높이의 몇 %를 머리가 차지할지"를 받아 그 크기가 되도록 3:4 를 잘라 낸다.
결과: 얼굴 위치 (50%, 30%) ✅ · 머리 크기 20% ✅ · 카드 85KB · 썸네일 38KB.
**이게 파이프라인의 결론이다 — 생성은 소재를 만들고, 규격은 크롭이 맞춘다.**

남은 것: 배경 관중이 2.8 절의 보케보다 또렷하고, 1호와 2호의 화풍이 다르다(8.2 편차 QA는 같은 모델·같은 파라미터로
3명을 만든 뒤에 판정해야 한다).

### 5.4 히어로 시험 3호 — **화풍은 프롬프트보다 모델이 결정한다**

2호를 본 사용자의 평가: *"처음 내가 만든 이미지가 더 좋은데 지금은 초등학교 만화 같다."* 맞는 지적이었고, 원인은 두 개다.

**① 스타일 문구가 납작함을 요구하고 있었다.** 자연어 프롬프트에 `flat vivid colors, clean lineart, cel shading` 이 들어 있었다.
이건 태그형에서 가져온 문구인데, 태그형은 **애니메 특화 SDXL** 을 전제한다 — 거기서 이 태그들은 "애니메 화풍"이라는 뜻이다.
**범용 모델은 같은 단어를 문자 그대로 받는다.**

**② 모델이 애니메용이 아니었다.** Nano Banana(Google)는 범용·실사 지향이다.

| | 2호 (Nano Banana + flat 문구) | 3호 (Seedream 4.5 + 밀도 문구) |
|---|---|---|
| 셰이딩 | 단색 2단, 굵고 균일한 외곽선 | 에어브러시 계조, 선 굵기 변화 |
| 머리카락 | 덩어리 | 가닥별 스페큘러 |
| 눈 | 하이라이트 1개 | 다중 하이라이트, 발광 |
| 조명 | 평면 | 림라이트·블룸·플레어·보케 |

바꾼 문구(자연어형에만 적용, 태그형은 그대로 둔다):

```
Premium mobile gacha game character card illustration — high-detail anime key visual,
semi-realistic anime rendering with soft airbrushed shading, glossy specular highlights,
individually rendered hair strands, luminous skin, rich colour depth, delicate varying line weight,
large expressive eyes with multiple highlights, subtle bloom and lens flare.
NOT flat colours, NOT simple cartoon, NOT thick uniform outlines, NOT a children's comic.
```

**확정**: 자연어형은 **Seedream 4.5**(`quality: high`, 3:4). Nano Banana 계열은 쓰지 않는다.

### 5.5 프롬프트로 안 잡히면 **편집 패스**로 고친다

Seedream 4장이 4장 모두 배꼽을 드러냈다(1.4 위반). 대문자로 못박아도 마찬가지였다.
프롬프트를 계속 다투는 대신, **생성된 그림을 그대로 참조로 넣고 옷만 고치게** 했다:

```
model: seedream_v5_pro
medias: [{ value: <media_id>, role: 'image_references' }]
prompt: "Edit this illustration: make the violet jersey longer so its hem overlaps the top of the
         shorts, completely covering her stomach — no bare skin. Keep everything else exactly as it is:
         same character, face, pose, ball, background, lighting and art style."
```

원본 URL 은 `media_import_url` 로 `media_id` 를 받아 넘긴다. 얼굴·포즈·조명·화풍이 유지된 채 옷만 바뀐다.
**42명에 쓸 수 있는 수법이고, 리터치 공정(8절)의 일부를 자동화한다.**

이렇게 해서 p001 최종본은 규격을 전부 통과한다 — 얼굴 (50%, 30%) · 머리 20% · 카드 94KB · 썸네일 45KB ·
글자 없음 · 민무늬 신발 · 공식구 색 · 배 가림.

## 7. 등급 상향 (v0.2) — 규정이 그림을 죽이고 있었다

히어로 시험 3호까지 오고 나서 드러난 것: **12세 금지선이 경기 장면의 박진감까지 같이 잘라 내고 있었다.**
"엉덩이·가슴 중심 프레이밍 금지", "땀은 얼굴·목·팔에만", "밀착 부위 형태 강조 금지", "배꼽 노출 금지" 를
프롬프트에 그대로 옮기면 모델은 **동작 자체를 밋밋하게** 그린다 — 점프가 낮아지고, 근육이 사라지고,
땀과 흐름이 없어진다. 규정을 지킨 결과가 "배구 카드처럼 안 보이는 배구 카드"였다.

`art-style-guide.md` 1.4 를 다시 썼다.

- **목표 등급 12세 → 15세.** 한 번 청소년이용불가까지 열기로 했다가 되돌렸다 —
  실제로 원한 것이 "경기의 박진감과 선수의 매력"이었고 그건 15세 안에서 전부 되며,
  19세는 원하지 않는 것(나체·성행위)을 허용하는 대신 심의·스토어·광고 제약만 남기기 때문이다(1.4.3).
- **1.4.1 을 신설했다 — 금지선이 아니라 요구 사항이다.** 높이·힘·긴장·속도·동작에서 나오는 실루엣·
  몸에 맞는 유니폼·전신의 땀·아끼지 않는 조명. **이게 없으면 QA 탈락**이다.
- 금지선(1.4.2)은 나체·속옷·과도한 노출·성행위·투시·업스커트·부위 클로즈업·아동형 체형으로 좁혔고,
  **실존 브랜드와 화면 내 문자는 등급과 무관하게 유지**한다.

프롬프트 생성기도 같이 바꿨다. `Modest sports illustration, no emphasis on chest, hips or thighs` 와
`loose-fitting`·`midriff covered` 문장을 걷어내고, 1.4.1 을 한 문장으로 요구한다:

```
Give it the intensity of a real match: she is at the very top of her jump with her feet clearly off the
floor, the low angle exaggerating her height and reach; an athlete's muscle definition visible in her
arms, shoulders and thighs; a fierce competitive expression with her eyes locked on the ball; hair,
jersey and beads of sweat all streaming in the direction of the motion.
```

네거티브에서도 `ass focus, thigh focus, hip focus, breast focus, skin tight shorts, wet thighs` 를 뺐다 —
이것들이 박진감을 죽이던 항목이다. `nsfw, nude, underwear, see-through, upskirt` 는 남긴다.

**결과**: 같은 모델·같은 크롭 규칙으로 도약·근육·땀·시선이 살아난 카드가 나왔다. 규격도 전부 통과
(얼굴 (50%, 30%) · 머리 20% · 카드 98KB · 썸네일 36KB).

### 7.1 남은 QA 항목

- **머리 모양이 데이터와 다르다.** p001 은 `롱 하이 포니테일`(하나)인데 생성물은 트윈테일이다.
  헤어스타일은 42명 구분의 1축(world.md 6.2)이라 그냥 넘길 수 없다 — 생성 시 강조하거나 편집 패스로 고친다.
- 배경 관중이 2.8 절의 보케보다 또렷하다.
- 화풍 편차 판정(8.2)은 같은 모델·같은 파라미터로 히어로 3명을 만든 뒤에 한다.

## 8. 화풍 확정 (v0.3) — "더 리얼하게"

15세 규정판까지 와서 나온 평가: *"더 디테일해야 할 것 같은데 부족해. 더 리얼하게 그렸으면 좋겠어."*
스타일 문구를 **묘사 밀도** 쪽으로 한 번 더 밀었다.

| 판 | 스타일 문구 | 결과 |
|---|---|---|
| v0.1 | `flat vivid colors, clean lineart, cel shading` | 납작한 만화 |
| v0.2 | `soft airbrushed shading, glossy highlights, per-strand hair, luminous skin` | 가챠 카드 수준 |
| **v0.3** | **`rendering pushed close to realism` — 피부 텍스처·subsurface·가닥별 헤어·직물의 짜임과 봉제선·해부학적 근육·손가락 힘줄·개별 땀방울·볼류메트릭 조명** | 반실사 키비주얼 |

모델도 `seedream_v4_5` → **`seedream_v5_pro`**(2k)로 올렸다.

### 8.1 편집 패스의 한계 — 옷은 고치고 머리는 못 고친다

p001 의 헤어스타일이 데이터(`롱 하이 포니테일`)와 달리 트윈테일로 나와서 편집 패스로 고치려 했으나
**4장 모두 실패**했다. 옷의 마크 제거·밑단 연장은 되는데, 헤어스타일은 **구조 변경**이라 안 된다.

| 수정 종류 | 편집 패스 | 재생성 |
|---|---|---|
| 옷의 로고·마크 제거 | ✅ | — |
| 상의 밑단 길이 | ✅ | — |
| 색 교체 | ✅(미검증) | — |
| **헤어스타일** | ❌ | ✅ |
| 포즈·구도 | ❌ | ✅ |

그래서 생성기의 자연어 프롬프트에서 헤어를 **대문자 전용 문장**으로 분리했다:
`HER HAIR: long platinum blonde hair worn in a high ponytail — exactly this and nothing else.`
재생성 한 번에 단일 포니테일이 나왔다.

**규칙**: 헤어·포즈가 틀리면 재생성, 옷·마크가 틀리면 편집 패스. 편집이 싼데 안 되는 것이 있다.

## 9. 미디엄 샷 — 크롭 손실을 없앤다 (v0.4)

전신 샷은 8라운드 내내 머리가 프레임의 **10~16%** 로 나왔다. 4.2 규격은 18~23% 이고,
`--headfrac` 로 잘라 맞출 수는 있지만 **원본의 일부만 쓰게 되어 해상도가 깎인다**.

프롬프트 맨 앞에 프레이밍을 못박으니 해결됐다:

```
MEDIUM SHOT / WAIST-UP CROP. The bottom edge of the frame cuts her off at mid-thigh —
her lower legs and feet are NOT in the picture. Her head, shoulders and torso fill most
of the frame; her head alone is about one fifth of the total image height.
This is a close hero portrait, not a full-body shot.
```

| | 전신 샷 (v0.3) | 미디엄 샷 (v0.4) |
|---|---|---|
| 원본에서 머리 크기 | 11% | **19.6%** |
| 규격(18~23%) | ✗ | **✅ 크롭 전에 이미 통과** |
| 크롭이 쓰는 원본 면적 | 약 30% | **약 96%** |
| 카드 해상도 손실 | 있음 | **거의 없음** |

**"화면의 1/5" 같은 비율 지시는 안 먹히고, "무릎 아래는 프레임 밖" 같은 물리적 지시는 먹힌다.**
모델은 비율을 못 세지만 무엇을 자를지는 안다.

세트 프롬프트 순서도 중요했다 — 프레이밍 문장을 **맨 앞**에 두어야 한다. 스타일·인물 묘사 뒤에 두면 묻힌다.

## 10. 캐릭터당 그림 두 장 — 카드와 전신

미디엄 샷과 전신 중 하나를 고르는 대신 **둘 다 쓴다.** 쓰이는 자리가 다르다.

| 슬롯 | 파일 | 프레이밍 | 쓰이는 곳 |
|---|---|---|---|
| 카드 | `{pid}_card.webp` | **미디엄 샷**(허벅지 컷) | 스카우트 결과·리스트. 96px 로 줄어도 얼굴이 읽혀야 한다 |
| 썸네일 | `{pid}_thumb.webp` | 얼굴 크롭(카드에서 자동) | 로스터·라인업·육성 목록의 원형 초상 44px |
| 전신 | `{pid}_hero.webp` | **전신 액션** | 선수 상세 화면 상단 전체 폭 배너. 점프의 박력을 크게 본다 |

프롬프트 팩은 캐릭터당 **CARD 와 HERO 두 문단**을 낸다. 차이는 **맨 앞 프레이밍 문장 하나**뿐이고
나머지(화풍·인물·유니폼·조명·등급 규정)는 완전히 같다 — 그래야 두 장이 같은 캐릭터로 보인다.

```bash
node tools/art-import.mjs p001 medium.png --face 897,732,460 --headfrac 0.20   # 카드 + 썸네일
node tools/art-import.mjs p001 full.png   --kind hero                          # 전신 (자르지 않는다)
```

전신은 크롭하지 않는다 — 화면에서 전체를 보는 그림이라 얼굴 위치를 맞출 이유가 없다.

**용량**: 1인당 카드 97KB + 썸네일 41KB + 전신 97KB = 235KB → **42명이면 약 9.6MB**, 예산 11MB 안.
`node web/art-pack.mjs` 가 지금 넣은 것의 1인당 평균으로 42명 추정치를 같이 찍는다 —

**화면**: `heroBanner()` 가 전신을 전체 폭 3:4 로 깔고 아래를 배경색으로 그라데이션 페이드한다.
전신이 없는 카드는 지금까지처럼 작은 카드 아트가 나온다 — 41명이 아직 그 상태이고, 한 명씩 들어와도 화면이 깨지지 않는다.

## 11. 히어로 3명 — 편차 QA 결과 (8.2절)

포지션·등급·구단이 갈리는 셋으로 "42명이 한 화풍으로 보이는가"를 판정했다.
같은 모델(`seedream_v5_pro`)·같은 설정(3:4 · 2k)·**같은 프롬프트 뼈대**로 뽑았다.

| pid | 이름 | 포지션 | 등급 | 구단 | 헤어 | 유니폼 |
|---|---|---|---|---|---|---|
| p001 | 서하율 | OH | SSR | 가온(t01) | 플래티넘 블론드 하이 포니테일 | 바이올렛 + 사이언 |
| p007 | 문반디 | L | R | 가온(t01) | 브라운 사이드 브레이드 | **시안 리베로** + 바이올렛 |
| p023 | 방한결 | MB | SSR | 적동(t04) | 블랙 크롭 숏컷 | 크림슨 + 카퍼 |

**통과한 것**

- **화풍이 갈리지 않는다.** 묘사 밀도·선·셰이딩·공 디자인·조명 처리가 셋 다 같은 계열로 읽힌다.
- **44px 원형 초상에서 세 명이 구분된다** — 헤어 색과 유니폼 색이 실루엣 없이도 갈린다.
- **리베로 규칙이 그림에 반영됐다**(5.4). 문반디만 팀 대비색(시안)이라 카드만 봐도 리베로다.
- 포지션별 포즈가 각각 스파이크·디그·블로킹으로 나와 역할이 읽힌다.

**드러난 문제**

| # | 문제 | 원인 | 대응 |
|---|---|---|---|
| 1 | **배경 명도가 크게 갈린다.** 문반디(R)는 밝은 주간 체육관, 나머지 둘(SSR)은 어두운 야간 아레나 | 등급별 조명 차등(6.4)이 **의도대로** 작동한 결과 — R `soft gym lighting` vs SSR `dramatic rim light + spotlight` | 등급 차등은 유지하되 **배경 명도 범위를 좁힐지** 결정 필요. 리스트에 섞이면 R 카드만 흰 판처럼 튄다 |
| 2 | 문반디의 머리가 프레임의 **31%**(규격 18~23%) | 디그는 몸이 낮고 카메라가 가까워 자연히 얼굴이 커진다. 크롭으로는 **줄일 수 없다**(화면 밖을 만들 수 없다) | 리베로·세터처럼 낮은 자세 포즈는 프롬프트에 거리를 더 주거나, 규격 밴드를 포지션별로 다르게 잡는다 |
| 3 | 방한결이 민소매 | 프롬프트는 `short sleeves` | 경미. 리터치 또는 편집 패스 |

**결론**: 화풍 편차는 없다. 42명으로 확대해도 된다.
다만 **① 등급별 배경 명도**와 **② 낮은 자세 포지션의 얼굴 크기**는 42명을 만들기 전에 정하는 편이 싸다.
