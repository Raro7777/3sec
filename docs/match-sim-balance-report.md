# 경기 시뮬레이션 몬테카를로 밸런스 리포트 (v0.2)

> 대상: `sim/VolleySim.Core` 프로토타입, `SimConfig` 기본값. **앞부분(v0.2 절)이 현재 기본값의 결과**이고, 뒷부분 "v0.1 리포트(이력)" 는 포지션 가치 재캘리브레이션 전 결과를 참고용으로 그대로 보존한 것이다.
> 설계 문서: [match-sim.md](match-sim.md). 상수의 의미·수식은 그쪽을 참조(v0.2 판정식 변경은 6.4·6.6~6.9 절).

## 실행 방법·환경

```bash
# .NET 8 SDK (이 컨테이너에는 없어 dotnet-install 로 설치)
curl -sSL https://dot.net/v1/dotnet-install.sh | bash -s -- --channel 8.0 --install-dir $HOME/.dotnet
export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$PATH

dotnet build sim/VolleySim.sln -c Release
dotnet test  sim/VolleySim.sln -c Release          # v0.2: 39/39 통과 (v0.1: 38/38)
dotnet run --project sim/VolleySim.Cli -c Release -- --matches 2000 --seed 42 --commentary --out report.md
# 실제 로스터(파일의 앞 두 팀 = 가온 vs 해솔)
dotnet run --project sim/VolleySim.Cli -c Release -- --matches 600 --seed 42 --players data/players.json --teams data/teams.json
# 상수 오버라이드(재컴파일 없이 캘리브레이션 반복, v0.2 에서 추가)
dotnet run --project sim/VolleySim.Cli -c Release -- --matches 4000 --seed 7 --set Receive.LiberoRoleGain=1.8 --set Block.MbStrengthWeight=1.6
```

- 팀 소스: 시드 기반 랜덤 동급 팀(overall 67, 잡음 ±6, 표준 5-1 자동 라인업). **경기마다 새 로스터**를 생성해 특정 로스터 편향을 없앴다. `--players data/players.json --teams data/teams.json` 을 주면 파일의 앞 두 팀으로 같은 시나리오를 돌린다.
- 시나리오 간에는 같은 (시드, 경기 번호) 난수열을 쓰는 공통 난수법을 적용해 시나리오 간 차이의 분산을 줄였다.
- 승률의 표준오차: 2,000경기 기준 약 ±1.1%p. 표에서 ±2%p 이내 차이는 잡음으로 본다.
- 실행 시간: 2,000경기(이벤트 수집 포함) 2.2초, 전체 리포트(약 40개 시나리오 × 2,000경기) 약 25초.

## v0.2-0. 배경과 결정

v0.1 의 "해당 선수 1명만 전 스탯 +15" 승률 상승폭은 OH +14.6 / OP +12.8 / S +12.0 / MB +8.3 / L +7.8 %p 로, MB·L 1인이 OH 1인의 53~57% 였다. 실제 배구의 역할 차이와는 부합하지만, 카드 수집형 가챠에서 SSR 리베로·미들블로커를 뽑은 유저가 손해를 느끼면 안 된다는 기획 결정에 따라 **MB·L 1인 가치를 OH 1인의 80~85% 로 끌어올리되 포지션 역할 차이는 남기는** 부분 보정을 했다. 서브 공격성·클러치 구조는 손대지 않았고, 공개 API·이벤트/JSON 스키마·결정성은 그대로다(추가 상수가 모두 중립값이면 v0.1 과 비트 단위로 같은 결과가 나오는 것을 확인했다).

## v0.2-2. 포지션별 민감도 (해당 선수만 전 스탯 +15) — 핵심 결과

공식 표(2,000경기, seed 42, 경기마다 새 동급 로스터):

| 대상 | 인원 | 홈 승률 | 1인당 변화 v0.1 | 1인당 변화 v0.2 | OH 1인 대비 v0.1 → v0.2 |
|---|---|---|---|---|---|
| OH 1명만 +15 | 1 | 63.7% | +14.6%p | +14.2%p | 100% → 100% |
| S만 +15 | 1 | 62.2% | +12.0%p | +12.7%p | 82% → 89% |
| OH 2명 +15 | 2 | 74.0% | +12.8%p | +12.3%p | 88% → 86% |
| OP만 +15 | 1 | 59.4% | +12.8%p | +9.9%p | 87% → 69% |
| MB 2명 +15 | 2 | 70.5% | +6.9%p | +10.5%p | 47% → 74% |
| **MB 1명만 +15** | 1 | 60.6% | +8.3%p | **+11.1%p** | 57% → **78%** |
| **L만 +15** | 1 | 61.7% | +7.8%p | **+12.2%p** | 53% → **86%** |

2,000경기에서는 1인 효과의 표준오차가 약 ±1%p(OH 대비 비율로는 ±8%p)라 한 시드만으로는 80~85% 밴드 판정이 어렵다. 그래서 시드 4개를 풀링해(seed 42 × 2,000 + seed 7·1234·99 × 4,000 = **14,000경기/시나리오**) 추정했다:

| 대상 | 1인당 변화(풀링) | OH 1인 대비 | v0.1 대비 |
|---|---|---|---|
| OH 1명 | +12.6%p | 100% | −2.0 |
| OH 2명(1인당) | +11.8%p | 94% | −1.0 |
| S | +11.0%p | 87% | −1.0 |
| OP | +10.9%p | 87% | −1.9 |
| **MB 1명** | **+11.1%p** | **88%** | **+2.8** |
| MB 2명(1인당) | +10.0%p | 80% | +3.1 |
| **L** | **+11.3%p** | **90%** | **+3.5** |

풀링 비율의 표준오차 ≈ ±4.5%p. **판정: MB·L 모두 목표 하한 80% 를 넘었고, 상한 85% 를 3~5%p 상회(1 SE 안팎)**. 테스트 허용 범위(75~95%) 안이다. 상한에 정확히 맞추려면 `Receive/Dig.LiberoRoleGain` 2.0→1.8, `Block.MbStrengthWeight` 1.8→1.6 정도의 트림이 필요하다고 추정(82~84%)하지만, 반복 예산(5회) 안에서 잡음보다 작은 차이라 여기서 멈추고 열린 이슈로 남긴다.

**부작용(정직한 기록)**: OH·S·OP 의 1인 절대값이 각각 1~2%p 내려갔다(OH 14.6→12.6, OP 12.8→10.9, S 12.0→11.0). 원인은 승률 곡선(로지스틱)의 기울기 희석 — L·MB 가 팀 강도 분산에서 더 큰 몫을 차지하게 되면서 다른 한 사람의 한계 효과가 조금 줄었다. 팀 전체 민감도(전원 +5/+10)는 오히려 72→76 / 89→91% 로 소폭 올랐으므로 "스탯이 승률에 미치는 힘" 자체가 준 것이 아니라 **포지션 간 분배가 바뀐 것**이다. 결과적으로 포지션 순서는 v0.1 의 OH ≈ OP ≈ S ≫ MB ≈ L 에서 **OH(12.6) > OH2·L·MB·S·OP(모두 11%p 안팎)** 로 압축됐다 — "OH 가 최고, 나머지는 근접" 이며 완전 동등은 아니다.

## 11. 캘리브레이션에서 어려웠던 점

1. **대결당 기울기 ↔ 팀 승률 민감도의 긴장.** 개별 선수 수준의 현실(스파이크 85 vs 55 의 kill% 차이 15%p)을 맞추려면 k≈35~50 이 맞지만, 한 랠리에 6~8개의 대결이 있고 세트당 45랠리가 누적되므로 팀 전원 +5 가 승률 97% 가 된다. 팀 단위 게임성(업셋 가능성)을 우선해 k=120 으로 평탄화했고, 대신 유형·세트 품질 보정 로짓으로 역할 차이를 만들었다. 개별 스탯의 "체감"이 약하다고 판단되면 `StatSensitivity` 를 올리면 되지만 리그가 결정론적으로 바뀐다는 점을 문서화했다.
2. **지표 간 결합.** kill% 를 낮추면 랠리가 길어져 사이드아웃률이 떨어지고, 블로킹을 올리면 kill% 가 함께 떨어진다. `FirstBallKillLogit`(퍼스트볼 전용 보정)을 분리한 뒤에야 kill% 와 사이드아웃률을 독립적으로 맞출 수 있었다.
3. **선택 편향.** 리시버·디거를 가중치로 고르면 좋은 선수에게 공이 몰려 실측 에이스율·리시브 A 비율이 기준 상수와 어긋난다. 상수를 "동급 대결 기준"으로 정의하되 실측으로 보정했다.
4. **전술 슬라이더의 의미.** 순수 확률만으로는 효율 최고 유형(속공)에 몰빵하는 것이 최적이라 슬라이더가 무의미해진다. 예측 가능성 페널티 하나로 "섞어야 이득" 구조를 만들었고, 페널티 크기(1.2→0.6→0.4)를 세 번 조정해 몰빵의 손해가 "명확하되 즉사는 아닌" 수준(−7~−31%p)에 맞췄다.
5. **서브 공격성.** 레이팅 배율 방식은 평탄화된 k 아래에서 효과가 사라져, 에이스·리시브 품질 로짓에 직접 반영하는 방식으로 바꿨다. 강서브/안정서브가 ±2%p 안에서 중립이 되도록 범실 기준(5%↔15%)과 로짓(±0.375)을 맞췄다.

## 12. 열린 이슈

- 세트당 총 득점 44.2 는 목표 하한 근처. 듀스 비율 14.6% 는 자연스럽지만 25-18 류의 일방적 세트가 실제보다 조금 많을 수 있다. 트랜지션 비중을 늘리는 방향(`KillBase`↓ + `FirstBallKillLogit`↑)으로 45~46 점을 노릴 수 있다.
- MB·L 의 1인당 가치가 OH/OP/S 의 60% 수준. 카드 상품성 관점에서 조정 여부는 기획 결정 사항. → **v0.2 에서 보정 완료(v0.2-2 절: MB 88%·L 90%).**
- 팀 컨디션 ±5% 의 효과가 크다. 컨디션 시스템의 값 범위를 정할 때 이 리포트의 8절을 기준으로 삼을 것.
- 파일 팀(`data/players.json`)으로 실행하면 "경기마다 새 로스터"가 아니라 고정 두 팀이 되므로 지표가 그 두 팀의 특성에 종속된다. 데이터가 확정되면 6구단 라운드로빈 시나리오를 CLI 에 추가하는 것이 좋다.
- 플랫폼 간 비트 일치(IL2CPP vs .NET 서버)는 미검증. 설계 문서 10절 참조.
