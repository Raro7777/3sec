# 코어 루프 텍스트 프로토타입 — 육성 모드 C# 구현 + 콘솔 플레이 (prototype-play v0.1)

> 상태: 프로토타입. `docs/training-mode.md` v0.2 를 `sim/VolleySim.Training`(netstandard2.1)으로 구현하고, `sim/VolleySim.Play`(net8.0 콘솔)에서 "스카우트 → 육성 → 졸업 → 로스터/서포터 → 라인업 → 경기(6구단)"가 한 바퀴 도는 것을 확인했다. 규칙의 참조 구현(오라클)은 `tools/training-sim/train_sim.py` 이며, C# 구현은 이 오라클과 정책별 분포가 일치한다(4절).
> 이 문서는 실행 방법, 구현 범위, **설계 대비 편차**, 필요한 Core 변경, `--auto` 관찰 리포트를 담는다. 설계 문서(`training-mode.md`, `match-sim.md`, `GDD.md`)와 `data/*.json` 은 손대지 않았다.

## 1. 실행 방법

```bash
export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$PATH DOTNET_CLI_TELEMETRY_OPTOUT=1
dotnet build sim/VolleySim.sln
dotnet test  sim/VolleySim.sln            # Core 테스트 + Training 테스트(46개, 오라클 정합 포함)

# 대화형 코어 루프 (저장은 saves/club-<seed>.json, gitignore)
dotnet run --project sim/VolleySim.Play -- --seed 1 --club "새록 스프라우츠"

# 비대화: 입력 줄을 순서대로 공급 ('#' 주석·빈 줄 무시, '.' = Enter). 입력이 끝나면 조용히 종료한다.
dotnet run --project sim/VolleySim.Play -- --script sim/VolleySim.Play/scripts/demo.txt --seed 7

# 비대화: 정책으로 N회 자동 육성(스카우트 → 추천 서포터 → 육성 → 편입 → 자동 라인업)하고 회차마다 6구단과 각 M경기
dotnet run --project sim/VolleySim.Play -- --auto --runs 8 --seed 1 --matches 3 --policy optimal
dotnet run --project sim/VolleySim.Play -- --auto --runs 8 --seed 1 --matches 3 --opponent-growth 0.6   # 6구단을 잠재력 60% 성장시킨 상대로

# 검증용
dotnet run --project sim/VolleySim.Play -- --oracle-table --n 2000     # 문서 12절 정책표를 C# 으로 재현
dotnet run --project sim/VolleySim.Play -- --calibrate-eval --n 200    # 실제 시뮬 평가전 활약도 캘리브레이션 표
dotnet run --project sim/VolleySim.Play -- --help
```

옵션: `--load saves/x.json`(이어하기) · `--save 경로` · `--data data/`(기본: 상위 디렉터리에서 `data/players.json` 탐색) · `--commentary`(경기 전체 중계 자동 출력) · `--stub-eval`(평가전을 스텁 근사식으로) · `--policy safe|optimal|push|random|norest|spike`.

stdin 이 없을 때(`< /dev/null`)는 첫 프롬프트에서 "입력이 끝나 종료합니다"를 출력하고 정상 종료한다.

### 2.4 스텁 · 미구현

- **인연 이벤트(T7)**: 카드 `bonds[]` 데이터가 없어 미구현(오라클에도 없음).
- **랜덤 이벤트 풀 30개**: 스크립트의 카테고리 생성 규칙(스탯 50% / 피로 25% / 컨디션 25%, 분기 50%)으로 이벤트를 만들고 텍스트는 카테고리별 1종(6.5절 예시 활용). JSON 풀로 빼는 구조만 잡아 둠(`EventCatalog`).
- **스토리 이벤트**: 카드별 텍스트 대신 공용 3편. 보너스는 포지션 CORE3 기반(OH 는 스크립트와 동일).
- **경제**: 스태미나·코인·호감도·스카우트 평판 없음. 티켓/조각만. 서포터 슬롯 해금(1/3회 완주·첫 A) 없이 3슬롯 상시.
- **스킬 효과**: 힌트 → 고유 스킬 Lv 표시만(경기 미반영, Core 훅 부재).
- **케미스트리 누적·PvP·리그 일정·교체 AI**: 없음. 경기는 단판 홈 경기.
- **특훈 3종**: 체력 특훈·멘탈 캠프는 구현돼 있으나 기본 가중치가 포지션 특훈 100%(3.3 편차 #2).

## 3. 설계 대비 편차

오라클(스크립트) 정합을 우선했고, 문서와 스크립트가 다른 곳은 스크립트를 따랐다. 게임 규칙으로 바꿀 곳은 `TrainingConfig` 플래그로 열어 두었다.

| # | 항목 | 문서 | 구현 | 비고 |
|---|---|---|---|---|
| 1 | 특훈 유효 기간 | 3.4절 "등장 시 그 턴에만 유효" | **수락/거절될 때까지 유지**(스크립트 동작) | `TrainingConfig.SpecialPersistsUntilUsed = true`. false 로 두면 문서대로. 안전 정책의 힌트 6.7·특훈 수락은 이 동작에 의존한다 |
| 2 | 특훈 종류 | 포지션 60 / 체력 25 / 멘탈 15% | 기본 **포지션 100%** | `SpecialKindWeights`. 문서도 "시뮬은 포지션 특훈 기준"이라 오라클과 맞춤 |
| 3 | 스텁 평가전 컨디션 보정 | 7.2절 `+ 컨디션 보정` | 스텁에는 없음(스크립트 동일). **실제 시뮬 제공자**에는 ±8 적용 + `PlayerCondition` 배수 | |
| 4 | 실제 시뮬 활약도 공식 | "박스스코어에서 포지션별 공식" | `50 + 1.5×(핵심3−강도) + 컨디션 + Scale×(순기여 − 기대 순기여(Δ)) + 0.5×점수차`, σ ≈ 12 | 시뮬의 개별 대결 기울기가 평탄(k=120)해 1세트 박스스코어만으로는 기울기 1.5/점이 나오지 않았다(캘리브레이션 표: 순기여로만 계산 시 OH −10/0/+10 → 48/53/55). 평균은 근사식으로 두고 박스스코어·점수차를 편차로 반영. 캘리브레이션 값은 `SimEvaluationProvider.Params`, 재측정은 `--calibrate-eval` |
| 5 | 강도 → 상대 팀 | "해당 포지션 핵심3 평균 = 강도" | 생성기 overall = 강도 − `CoreOffset[pos]`(S 7.7 / OH 4.3 / OP 7.7 / MB 5.7 / L 13.7, 프로파일에서 계산). 캠프 팀 = 같은 overall 의 생성 12인에서 **같은 포지션 선발 자리**를 트레이니로 교체. 1세트 25점(`PointsToWinFinalSet` 도 25) | |
| 6 | 랜덤 이벤트 | 30개 풀, 조건부 등장 | 카테고리 생성 + 텍스트 1종씩. **첫 선택지 = 스크립트 평균 효과(오라클 선택지)**, 둘째는 사람용 대안 | 자동 정책은 항상 오라클 선택지를 고르므로 "야간 자율 훈련 [같이 남는다] → 피로 +10" 같은 손해 선택도 한다(5절 피드백) |
| 7 | 선배 이벤트 | 동문 70%, [배운다] 피로 +5 | 50% 고정, 피로 없음(스크립트) | |
| 8 | 졸업 등급 | 반올림 확정치 기준 | 인스턴스 등급은 반올림 기준, **오라클 비교는 소수 OVR**(`GraduationResult.OvrRaw`) | 차이 ≤ 0.5 |
| 9 | 부상 이력 | 인스턴스에 남기지 않음 | 동일. 캠프 기록에만 | |
| 10 | 한계돌파 | GDD 2.2 "중복 카드로 상한 해제" | 중복 스카우트 1회당 전 스탯 잠재력 +3 | 프로토타입 간이 규칙 |
| 11 | 6구단 로스터 | — | `players.json` **초기치 그대로**(스탯 평균 ≈ 52). `--opponent-growth g` 로 `초기치 + g×(잠재력−초기치)` 가정 가능 | 5절 |
| 12 | 연습생 | — | `RandomPlayerGenerator` overall 44(N, OVR 43~50) 7명. 졸업생이 생기면 자동 라인업에서 밀려남 | |
| 13 | 재화 | 스태미나 30/회 | 티켓(초기 5, 승리 +1, 첫 완주 +1), 조각(패배·방출 +1, 3개 = 티켓 1). `--auto` 는 티켓 무제한 | |
| 14 | 난수 | 파이썬 MT19937 | Core `DeterministicRandom`(xoshiro256**) | 수열은 다르고 **분포만** 일치. 정합은 n=2,000 몬테카를로로 확인 |
| 15 | 스토리 정답 | 카드별 | 공용 3편, 첫 선택지가 정답(힌트 +1) | |
| 16 | 서포터 편성 기억·슬롯 해금 | 11.4절 | 없음(매번 추천 편성) | |

## 4. 파이썬 오라클 정합 (SSR OH 예시 카드, 스텁 평가전)

`OracleTests`(n=2,000)와 `--oracle-table` 로 확인. 파이썬 값은 같은 스크립트를 n=2,000·seed 1(풀세팅은 seed 4)로 돌린 것, 문서 값은 12절(n=3,000).

| 정책 | 문서 v0.2 | 파이썬 (n=2,000) | **C# (n=2,000)** | 테스트 허용 오차 |
|---|---|---|---|---|
| 안전 | 76.2 (σ1.2) · A 97% · 부상 0% · 힌트 6.7 | 76.18 (1.16) · A 96.9 · 0.1% · 6.65 | **76.2 (1.2) · A 97 · 0% · 6.6** | OVR ±0.6 ✓ |

## 5. 필요한 Core 변경

**필수 변경 없음.** Core 는 수정하지 않았고 공개 API 만 사용했다. 다음은 있으면 좋은 것:

1. **활약도 공식의 소속**: 7.2절은 "활약도는 시뮬 코어가 박스스코어에서 산출"이라 하나, 현재 Core 에 없어 `SimEvaluationProvider.NetContribution/Performance` 에 두었다. match-sim 담당이 Core 로 옮길 때 이 함수를 기준점으로 쓸 수 있다. 단 4절의 "기울기 평탄" 문제 때문에 순수 박스스코어 공식은 1세트에서 성장 체감이 약하다(6.3절 피드백 #4).
2. **하이라이트 추출 API**: `KoreanCommentary.Render` 는 평문 리스트만 주므로 세트 종료 라인을 문자열(`"세트 종료"`)로 찾아 그 앞 4줄을 하이라이트로 쓴다. 이벤트 기반 `RenderHighlights(result, n)` 나 `SetEnd` 인덱스를 함께 돌려주면 안전하다.
3. **팀 상태에 선수 삽입 헬퍼**: `RandomPlayerGenerator.GenerateTeamState` 후 특정 포지션 선발을 바꾸는 API 가 없어 `Lineup.StartingIds` 슬롯(S 1 / OH 2 / MB 3 / OP 4 / L 리베로)을 직접 교체한다(`SimEvaluationProvider.InsertTrainee`). `LineupBuilder.Auto` 가 슬롯 위치를 바꾸면 깨질 수 있다.
4. `SimConfig.Clone()` 이 없어 `CreateDefault()` 에서 `Match` 필드만 덮어쓴다(1세트 25점). 기본값이 아닌 설정을 평가전에 넘기려면 `customizeSimConfig` 콜백을 쓴다.
5. `PlayerBoxScore` 에 "출전 랠리 수"가 없어 트레이니가 실제로 코트에 섰는지는 터치 합으로 추정한다.

### 6.4 프로토타입에서 느껴진 문제 (기획 피드백)

1. **6구단 로스터 강도가 양극단이다.** `players.json` 초기치 그대로면 연습생만으로도 6% 이기고, 졸업생 2~3명(OVR 60대 R 카드)이면 30~50%, 6명이면 70~90%. 반대로 잠재력 60% 성장 가정에서는 8회 육성해도 6~28%. 리그 상대를 "초기치 + 35% 성장"으로 두면 첫 승리 2~4회차, 8회차 승률 20~60%(6.2절)로 사다리가 생긴다. 여기에 구단별 티어(라온·태령 약, 연화·해솔 강)를 얹으면 "첫 승리는 약팀에게" 연출이 된다. 리그용 6구단 스탯(성장치)을 데이터로 확정해야 한다.
2. **R 80% 스카우트는 로스터 성장을 R 카드(졸업 OVR 57~68, 등급 C)에 묶는다.** 3시드 24회에서 SSR 0장, SR 4장. 첫 SSR 기대 스카우트 수 33회. 육성 8회 뒤 로스터 최고 OVR 이 74(SR A) 였다. 초기 보장(튜토리얼 SR+ 1장), 천장, 또는 포지션 지정 스카우트가 없으면 "내가 키운 에이스" 판타지가 늦게 온다. 한계돌파(중복 +3)는 8회 안에 1~2회 발생해 체감이 작다.
3. **포지션 편중으로 라인업에 구멍이 남는다.** 랜덤 스카우트라 시드 3 은 MB 4 / OH 2 로 S·OP·L 자리를 8회차에도 연습생이 채운다(연습생 3명). 세터가 연습생이면 공격 조립이 무너져 MB/OH 졸업생의 가치가 깎인다. 포지션 필터 스카우트, 포지션별 티켓, 또는 "부족 포지션 확률 가중"이 필요하다.
4. **실제 시뮬 평가전은 1세트로는 성장을 읽지 못한다.** 개별 대결 기울기가 평탄해 트레이니 핵심3 ±10 이 박스스코어 순기여를 ±1 정도만 움직인다(σ 2.6). 활약도 평균을 근사식으로 고정하고 박스스코어를 편차로 쓴 이유다(3절 #4). 결과적으로 MVP(≥80)는 스탯보다 운(σ 12)에 좌우된다. 평가전을 2세트로 늘리거나, 활약도 표시를 "기대 활약도 + 오늘의 편차"로 나눠 보여 주는 UI 가 필요하다. match-sim 의 `StatSensitivity` 를 평가전에서만 올리는 것도 후보.
5. **자동 진행의 이벤트 선택이 손해를 본다.** 정책은 정합을 위해 항상 오라클 선택지를 고르므로 "야간 자율 훈련 → 피로 +10", "감기 기운 → 컨디션 −1"을 자동으로 받는다. 11.2절의 "사전 설정(안전/공격) 규칙" 이벤트 선택기를 별도로 두고, 그 효과를 스크립트에도 반영해 수치를 다시 뽑아야 한다.
6. **티켓 경제가 초반에 막힌다.** 승리 +1 만 있으면 승률 10~20% 구간에서 5장이 곧 바닥난다. 프로토타입은 패배 조각(3개 = 1장)으로 메웠지만, 문서 10절의 스태미나·일일 미션 구조로 바꿀 때 "첫 승리 전 육성 5~6회"가 보장돼야 한다.
7. (관찰) 텍스트 턴 화면의 정보량은 문서 1.4절 상한 안에 들어갔고, 예상 상승치 3줄 + 부상 배지만으로 "핫존에서 숫자가 커진다"가 읽힌다. 다만 콜드존(휴식 직후 ×0.85)은 숫자만으로는 "왜 적게 오르지"가 남아 13절의 UX 이슈가 그대로 재현된다.
