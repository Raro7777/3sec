# 선수 고유 스킬 시스템 (skills v0.1)

> 상태: **JS 엔진 구현 완료**(`web/engine/skills.js`), 몬테카를로 캘리브레이션 3회 반영. C# (`sim/`) 은 아직 훅 인터페이스(`ISkillEffectProvider`)만 있고 미구현 — 이식 명세는 8절.
> 관련 문서: [match-sim.md](match-sim.md) 6절(판정식)·8절(변수) · [world.md](world.md) 5절(SSR 10명) · [training-mode.md](training-mode.md) 8.4절(힌트 → 스킬 레벨) · 검증 하네스 `web/parity.mjs` 7절

---

## 0. 한 줄 요약

스킬은 자유 서술이 아니라 **`{효과 타입, 채널, 대상, 조건, 계수}` 데이터 배열**이다. 발동하면 기존 판정식의 **로짓에 값을 더할 뿐**(확률을 곱하지 않는다), 난수를 새로 뽑지 않으며, 스킬 보유자가 0명이면 런타임 자체가 만들어지지 않아 **기존 경기 결과와 비트 단위로 같다**. 새 스킬은 `SKILLS` 배열에 데이터 1건을 추가하면 되고 엔진 코드는 건드리지 않는다.

## 1. 설계 원칙

| 원칙 | 구현 |
|---|---|
| 자유 서술 금지 | 24개 스킬 전부 3종 효과 타입 × 10개 채널 × 4종 대상 × 15종 조건의 조합으로 표현 |
| 로짓 가산만 | `Contest(base, diff, k, extra)` 의 `extra` 에 더한다. 확률을 직접 곱하는 경로는 없다 |
| 결정성 | 스킬 코드는 `Rng` 를 호출하지 않는다 → 난수 소비량 불변, 같은 시드 = 같은 결과 |
| 무보유 = 무영향 | 활성 스킬 0명이면 `createSkillRuntime` 이 `null` 을 돌려주고 `match.js` 가 훅을 건너뛴다 |
| 설명과 효과 일치 | `data/players.json` 의 한국어 설명이 명세다. 해석이 필요한 곳은 4·5절에 근거를 남긴다 |
| 데이터 확장 | 새 스킬 = `SKILLS` 배열에 1건 추가. 엔진 수정 불필요 |

## 2. 효과 모델

### 2.1 효과 타입 3종 (`EFFECT`)

| 타입 | 뜻 | 쓰는 스킬 |
|---|---|---|
| `logit` | 지정 채널의 로짓에 `mag × 레벨배수` 를 더한다 | 24개 전부 |
| `weight` | 공격 옵션 선택 가중치에 `×(1 + mult × 레벨배수)` | 순풍(속공 비중) |
| `fatigueImmune` | 그 선수의 해당 판정에서 스태미나 피로 감소를 면제 | 모루 위에서(블로킹) |

### 2.2 채널 10종 (`CH`) — 로짓이 실리는 판정 지점

| 채널 | 붙는 자리 (`match.js`) | 소유 팀 | + 부호의 뜻 |
|---|---|---|---|
| `serveError` | 서브 범실 `contest(...)` extra | 서브 | 범실↑ |
| `serveAce` | 에이스 `sigmoid(logit(aceBase) − x + …)` | 서브 | 에이스↑ |
| `servePressure` | 리시브 대결 `x` 에서 **감산** | 서브 | 상대 리시브 품질↓ |
| `receive` | 리시브 대결 `x` 에 가산 | 리시브 | 에이스 피격↓·패스 품질↑ |
| `set` | 토스 품질 `setX` | 공격 | A토스 확률↑ |
| `attackKill` | `killExtra` | 공격 | 결정률↑ |
| `attackError` | 공격 범실 `contest(...)` extra | 공격 | 범실↑ |
| `antiBlock` | `blockExtra` 에서 **감산** | 공격 | 피블로킹↓ |
| `block` | `blockExtra` | 수비 | 블로킹 득점·터치↑ |
| `dig` | `killExtra` 에서 감산 + 디그 품질 `dx` 에 가산 | 수비 | 디그 유리 |

`servePressure` 와 `antiBlock` 은 "상대의 판정을 내가 깎는다"를 부호 하나로 표현하려고 둔 채널이다. C# `SkillTrigger` 열거형(8개)에 이 둘을 추가하면 1:1 대응이 된다(8절).

### 2.3 대상 4종 (`TARGET`)

| 대상 | 발동 조건 |
|---|---|
| `self` | 보유자가 그 판정의 행위자(서버·리시버·공격수·디거·세터)일 때 |
| `setter` | 보유자가 **그 공격의 토스를 올린 세터**일 때 (세터 스킬이 공격수의 판정을 돕는 경우) |
| `blocker` | 보유자가 **그 블로킹에 참여 중**일 때 |
| `team` | 보유자가 코트에 있으면 팀 전체 판정에 |

공통 전제: **보유자가 코트에 있어야 한다.** 로테이션으로 후위에 있거나 리베로 교체로 빠지면 자동으로 꺼진다(`team.positionOf(p) !== 0`). 이것이 "코트에 없으면 스킬도 없다"는 배구다운 게이트 역할을 한다.

### 2.4 조건 15종 (`when`) — 전부 AND

| 키 | 뜻 |
|---|---|
| `minScoreFromEnd: n` | 보유 팀 점수 ≥ (세트 목표점 − n). n=5 → 25점제 20점, 5세트 10점 |
| `home: true` | 보유 팀이 홈 |
| `pointStreak: n` | 보유 팀 n연속 득점 중 |
| `concededStreak: n` | 보유 팀 n연속 실점 직후(= 상대 n연속 득점 중) |
| `maxRotations: n` | 세트 내 로테이션 횟수 < n |
| `afterOwnBlockKill` | 보유자가 **직전 랠리에** 블로킹 득점에 관여 |
| `strongServeReceived` | 보유자가 **이 랠리에** 상대 강서브를 A/B로 받아냄 |
| `types: [ATK…]` | 공격 유형(속공·오픈·후위·시간차·덤프) |
| `blockersMax / blockersMin: n` | 상대 블로커 수 |
| `passQuality: [Q…]` | 직전 접촉(리시브·디그)의 품질 |
| `minAttackIndex: n` | 랠리 내 공격 시퀀스 번호(0 = 퍼스트볼) ≥ n |
| `nonSetterToss` | 세터가 첫 터치를 해서 다른 선수가 2단 토스 |
| `topSpiker` | 공격수가 코트 위 스파이크 최고치 선수 |
| `opponentLiberoOff` | 상대 리베로가 코트 밖 |
| `minAggression: v` | 서브 공격성 ≥ v |

### 2.5 데이터 예시

```js
{
  id: 'spotlight', name: '스포트라이트', owner: 'p001', rarity: 'SSR', pos: POS.OH,
  effects: [
    L(CH.attackKill, TARGET.self, 0.34, { minScoreFromEnd: 5 }),              // 20점 이후
    L(CH.attackKill, TARGET.self, 0.17, { minScoreFromEnd: 5, home: true }),  // 홈이면 추가
  ],
}
```

## 3. 스킬 레벨

`training-mode.md` 8.4 의 힌트 임계값(3/6/9)이 그대로 레벨 1/2/3 이 된다. 레벨은 **계수 배수**로만 작용한다.

| 레벨 | 배수 (`config.skill.levelScale`) | 도달 조건 |
|---|---|---|
| 0 | 0.0 (스킬 미발동) | 힌트 < 3 |
| 1 | 1.0 | 힌트 ≥ 3 |
| 2 | 1.5 | 힌트 ≥ 6 (최적/안전 정책의 평균 도달점) |
| 3 | 2.0 | 힌트 ≥ 9 (최적 정책 약 30%) |

레벨 3 = 레벨 1 의 정확히 2배로 잡은 것은 목표 밴드(Lv1 +1~3%p, Lv3 +3~6%p)의 중앙값 비율이 2:1 이기 때문이다. 실측에서도 승률 기여가 계수에 거의 선형이라 배수 비율이 그대로 승률 비율로 나온다(6.2절 표의 Lv3 ÷ Lv1 ≈ 2.0~2.2).

## 4. SSR 10명 — 해석과 수치

계수 `mag` 는 **Lv1 기준 로짓**이다. 실제 값 = `mag × levelScale[레벨] × globalScale × 중첩감쇠`.

### 4.1 p001 서하율 — 스포트라이트 (OH)
> 세트 스코어 20점 이후 자신의 스파이크 성공률이 상승한다. 홈 경기에서는 상승 폭이 더 커진다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 20점 이후 결정률 | attackKill | self | `minScoreFromEnd: 5` | +0.34 |
| 홈 추가분 | attackKill | self | `minScoreFromEnd: 5` + `home` | +0.17 |

**해석**: "20점"은 25점제 기준이므로 세트 목표점 −5 로 일반화했다(5세트는 10점 이후). 클러치(2점차 이내) 조건은 붙이지 않는다 — 설명에 없다.

### 4.2 p002 탁세온 — 천둥 왼손 (OP)
> 후위 공격(백어택) 시 파워가 상승한다. 상대 블로커가 1인 이하일 때 결정률이 크게 오른다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 백어택 파워 | attackKill | self | `types:[BackRow]` | +0.11 |
| 백어택 파워(범실 감소) | attackError | self | `types:[BackRow]` | −0.05 |
| 블로커 1인 이하 | attackKill | self | `blockersMax: 1` | +0.14 |

**해석**: 두 문장이 독립이므로 두 번째 효과는 **모든 공격 유형**에 적용한다. "파워 상승"은 엔진에 파워 스탯을 올리는 경로가 없어 그 파워가 만드는 결과(결정률↑ + 범실↓) 두 채널로 옮겼다.

### 4.3 p008 백윤슬 — 닻을 내리다 (L)
> 상대의 강서브를 리시브에 성공하면 그 랠리 동안 팀 전체의 디그 성공률이 상승한다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 팀 디그 | dig | team | `strongServeReceived` | +0.25 |

**해석**: (1) "강서브" = 서브 팀 공격성 ≥ 0.5(기본 전술값). 안전 서브 전술(<0.5)에는 발동하지 않는다. (2) "리시브에 성공" = **보유자 본인**이 리시버였고 결과가 A 또는 B 패스. C패스는 "흔들린 것"이므로 성공으로 보지 않는다. (3) 효과는 그 랠리가 끝날 때까지만 유지된다.

### 4.4 p009 하담희 — 등대 (OH)
> 팀이 2연속 실점하면 발동한다. 다음 랠리에서 팀 전원의 리시브와 멘탈이 상승한다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 팀 리시브 | receive | team | `concededStreak: 2` | +0.10 |
| 팀 멘탈(공격 범실) | attackError | team | `concededStreak: 2` | −0.07 |
| 팀 멘탈(서브 범실) | serveError | team | `concededStreak: 2` | −0.07 |

**해석**: `mental` 스탯은 엔진에서 클러치 실효 배수에만 쓰여 랠리 단위로 "올릴" 수 없다. 그래서 **멘탈 상승 = 그 랠리 동안 팀이 덜 흔들린다**로 옮겨 공격·서브 범실 로짓을 낮췄다. 연속 실점이 3, 4로 이어져도 효과는 그대로다(2 이상이면 계속 켜짐).

### 4.5 p015 한새봄 — 설벽(雪壁) (MB)
> 블로킹 득점을 올리면 다음 랠리 동안 팀 전체의 블로킹 성공률이 상승한다. 상대의 오픈 공격에 특히 강하다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 다음 랠리 팀 블로킹 | block | team | `afterOwnBlockKill` | +0.13 |
| 오픈 공격 상대 | block | blocker | `types:[Open]` | +0.13 |

**해석**: "블로킹 득점을 올리면" = 그 블록에 **참여한 전원**(주 블로커 + 보조)을 성공으로 본다. 주 블로커만으로 한정하면 발동 빈도가 3분의 1로 떨어져 스킬이 사실상 죽는다.

### 4.6 p022 천유하 — 달군 쇠 (OP)
> 팀이 2점 이상 연속 득점 중일 때 자신의 스파이크 파워와 성공률이 상승한다. 연속 득점이 끊기면 초기화된다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 결정률 | attackKill | self | `pointStreak: 2` | +0.70 |
| 파워(범실 감소) | attackError | self | `pointStreak: 2` | −0.30 |

**해석**: 연속 득점 카운터는 랠리 종료마다 갱신되고 실점하면 0 이 된다("초기화"). 세트가 바뀌어도 0 이다. 조건이 좁은 대신 계수가 크다 — 발동 순간의 체감을 위한 의도적 설계(Lv3 에서 킬 로짓 +1.4 = 결정률 41% → 71%).

### 4.7 p023 방한결 — 모루 위에서 (MB)
> 세트 20점 이후에도 스태미나 저하로 인한 블로킹 페널티를 받지 않는다. 상대 속공 블로킹 성공률이 상승한다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 피로 면제 | *fatigueImmune* | blocker | `minScoreFromEnd: 5` | — |
| 상대 속공 블로킹 | block | blocker | `types:[Quick]` | +0.45 |

**해석·주의**: 피로 면제는 **블로킹 강도 계산(`weightedBlockRating`)에만** 적용한다. 스태미나 80 인 선수가 5세트 후반에 잃는 값은 실효 배수 1.5% 남짓(match-sim 5.2)이라 **승률 기여가 사실상 0**이다. 설명에 있으니 정직하게 구현했고, 이 스킬의 실제 힘은 두 번째 효과에서 나온다. 레벨이 올라도 면제 자체는 커지지 않는다(면제는 0/1).

### 4.8 p029 소이든 — 한 수 앞 (S)
> 랠리가 3회 이상 이어진 뒤의 토스에서 시간차·이동 공격 성공률이 상승한다. 상대 블로커 위치를 예측하는 보너스를 받는다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 시간차·이동 공격 | attackKill | setter | `minAttackIndex: 2` + `types:[Delayed, Quick]` | +0.24 |
| 블로커 위치 예측 | antiBlock | setter | `minAttackIndex: 2` | +0.14 |

**해석**: (1) "랠리가 3회 이상 이어진" = 그 랠리의 **세 번째 공격 시퀀스부터**(`attackIndex ≥ 2`). (2) 엔진에 "이동 공격(슬라이드)" 유형이 없어 **MB 의 속공(Quick)** 으로 본다(4.10·5절 공통 규칙).

### 4.9 p030 위채운 — 학의 날개 (OH)
> 상대 블로커가 2인 이상일 때 페인트와 코스 공략으로 스파이크 성공률이 상승한다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| 블로커 2인 이상 | attackKill | self | `blockersMin: 2` | +0.165 |

**해석**: 블로커가 많을수록 강해지는 유일한 스킬. 조건이 흔해(오픈 공격의 약 70%가 2인 블록) 계수가 작다.

### 4.10 p036 도리원 — 순풍 (S)
> 리시브가 정확(A패스)했을 때 속공과 이동 공격 성공률이 크게 상승한다. 랠리 템포가 빨라진다.

| 효과 | 채널 | 대상 | 조건 | mag |
|---|---|---|---|---|
| A패스 속공 결정률 | attackKill | setter | `passQuality:[Perfect]` + `types:[Quick]` | +0.225 |
| 랠리 템포 | *weight*(속공) | setter | `passQuality:[Perfect]` | ×(1 + 0.11) |

**해석**: "템포가 빨라진다"를 **속공 선택 비중 증가**로 옮겼다(Lv3 에서 속공 후보 가중치 ×1.22). 가중치를 바꿔도 `weightedIndex` 호출 횟수는 그대로라 난수 소비량은 변하지 않는다.

## 5. SR 14명 — 해석과 수치

SR 스킬도 **같은 시스템**으로 처리한다. R 18명은 `data/players.json` 에 스킬이 없어 **미적용**이다(스킬 필드가 빈 문자열 → 레벨 0 → 판정 무영향).

### 6.3 중첩 감쇠 (`stackFalloff`)

스킬 6개를 단순 합산하면 선형에 가까워져(감쇠 없이 +19.6%p) 상한을 넘는다. 그래서 **코트 위 스킬 보유자 수 n 에 따라 개별 효과를 감쇠**한다.

```
개별 효과 × 1 / (1 + stackFalloff × (n − 1)),  stackFalloff = 0.06
n = 1 → ×1.000   n = 3 → ×0.893   n = 6 → ×0.769
```

n=1 에서 1.0 이므로 **단독 기여 캘리브레이션(6.2)은 감쇠의 영향을 받지 않는다.** 서사적으로는 "에이스가 여럿이면 서로의 몫을 나눠 갖는다"에 해당한다. n 은 랠리 시작마다 다시 센다(로테이션·리베로 교체로 코트 밖에 있는 보유자는 세지 않는다).

### 7.2 스킬 레벨은 어디서 오는가

| 대상 | 레벨 | 근거 |
|---|---|---|
| 플레이어가 육성한 카드 | 힌트 임계값 3/6/9 → **Lv1~3** (`instanceToPlayer` 가 인스턴스의 `skillLevel` 을 그대로 넘긴다) | training-mode 8.4 |
| 플레이어의 연습생(N) | 0 | 스킬 없음 |
| **AI 6구단 원소속 선수** | **시즌 1 = Lv2, 시즌 2+ = Lv3** (`CLUB_SKILL_LEVEL = [2,3,3,…]`, `game.js`) | 아래 |
| 파리티 하네스의 랜덤 생성 선수 | 0 | 생성기가 붙이는 스킬 이름은 레지스트리에 없고 레벨도 0 |

**AI 구단 규칙의 근거.** 서하율은 원래 가온 프리즘의 간판이다. 세계관상 그 선수가 자기 구단에서 뛸 때 고유 스킬이 꺼져 있을 이유가 없으므로 **AI 구단 선수도 스킬을 쓴다.** 레벨을 시즌 1부터 Lv2 로 둔 것은 두 가지 이유다.

1. **서사**: 원소속 SSR·SR 은 이미 그 스킬로 리그에서 이름을 낸 완성형 주전이고, 플레이어가 갓 졸업시킨 신인은 힌트로 숙련도를 쌓아가는 중이다. 스탯 사다리(`SEASON_GROWTH` 52%→80%)와 같은 속도로 Lv3 에 도달한다.
2. **난이도**: Lv1 로 두면 플레이어의 육성 카드(평균 Lv2)가 원소속보다 스킬까지 앞서 시즌 1 우승률이 22.5% 로 목표(≤20%)를 넘었다. Lv2 시작으로 바꾸니 12.0% 가 되어 스킬 도입 전(16.5%)과 비슷하거나 약간 어려운 수준으로 돌아왔다.

`clubTeamState(state, clubId, { clubSkillLevel: n })` 로 호출 단위 재정의가 가능하다(0 = 완전히 끄기).

## 8. C# 이식 명세 (`sim/VolleySim.Core`)

현재 C# 은 `Skills/ISkillEffectProvider.cs` 에 훅 인터페이스만 있고 구현이 없다(`SimConfig.SkillProvider = null`). 이식 시 필요한 작업:

1. **`SkillTrigger` 열거형 확장** — 기존 8개(`ServeError, ServeAce, Receive, Set, AttackError, AttackKill, BlockKill, Dig`)에 `ServePressure`, `AntiBlock` 을 추가해 10개로. `BlockKill` 은 `Block` 으로 이름을 맞추는 편이 낫다(터치 판정에도 같은 로짓이 실린다).
2. **인터페이스 교체** — 현재 시그니처(`actor, opponent, setIndex, homeScore, awayScore, clutch`)로는 조건 15종을 판정할 수 없다. `readonly struct SkillContext` 를 만들어 `Trigger, Side, Actor, Setter, Attacker, Blockers(ReadOnlySpan<Player>), AttackType, AttackIndex, PassQuality, SetQuality, BlockerCount, Aggression, OwnScore, PointsToWin, PointStreak, Rotations, LiberoOffCourt` 를 넘긴다.
3. **`Player` 에 `SkillLevel` 추가**(int, 기본 0) — `JsonDataLoader.ParsePlayer` 가 `skill.level` 을 읽되 없으면 0. `data/players.json` 에는 아직 `level` 필드가 없다(레벨은 런타임에 주입된다).
4. **`SkillTable` 정적 레지스트리** — `web/engine/skills.js` 의 `SKILLS` 배열을 그대로 옮긴다. 효과는 `readonly struct SkillEffect { EffectKind Kind; Channel Ch; Target Target; double Mag; SkillCondition When; }`. `SkillCondition` 은 `int?`/`byte[]` 필드 묶음(전부 null = 상시).
5. **`SkillRuntime` 클래스** — `MatchContext` 가 경기 시작 시 1개 생성. 상태: `int[2] streak`, `int[2] rotations`, `int[2] lastRotationIndex`, `double[2] stackMult`, 엔트리별 `blockKillPrev/blockKillThis/strongRecv`. **난수를 쓰지 않는다.**
6. **`RallyEngine` 훅 15곳** — 7.1절 표와 같은 위치. 전부 `if (skills != null)` 가드. `MatchContext.EffectiveMultiplier` 에 `bool noFatigue` 인자 추가(모루 위에서).
7. **`SimConfig.Skill`** — `Enabled(bool)`, `LevelScale(double[4])`, `ChannelCap(1.5)`, `GlobalScale(1.0)`, `StackFalloff(0.06)`.
8. **검증** — `SkillTests`: (a) 스킬 0명이면 `Signature()` 가 v0.2 골든과 완전 일치, (b) 같은 시드 재현, (c) 난수 소비량(`RandomDraws`)이 스킬 유무와 무관하게 동일, (d) 스킬 1개 Lv1/Lv3·6개 Lv3 의 승률 밴드(6.1절). (c)는 JS 구현에서도 성립하는 강한 불변식이라 이식 정합의 기준으로 쓸 만하다.
9. **주의** — JS 와 C# 의 스킬 결과가 **비트 단위로 같을 필요는 없다**(랠리 전개가 갈리면 난수 스트림이 달라진다). PARITY.md 의 기존 방침대로 **집계 일치**를 목표로 한다. 단 "스킬 0명 = 기존과 완전 일치"는 양쪽 모두에서 비트 단위로 성립해야 한다.

## 9. 열린 이슈

- [ ] **고공 낙하·2단 토스가 목표 밴드 미달**(Lv3 +0.2%p 수준). 원인은 계수가 아니라 발동 빈도다. 고공 낙하는 "OP 가 블로킹 득점에 관여한 다음 랠리에 본인이 공격"이 랠리의 1% 미만이고, 2단 토스는 리베로가 대체 세터로 뽑히는 경우 자체가 드물다(`chooseAlternativeSetter` 의 리베로 −10 페널티). 설명을 바꾸거나(예: "블로킹 터치 이후"), 대체 세터 선택 로직에 리베로 세트 감각을 반영해야 한다.
- [ ] **6스킬 Lv3 이 상한(18%p)과 여유가 크지 않다**(측정 16.71%p, 95% CI 상단 18.3%p). 더 여유를 원하면 `stackFalloff` 를 0.10~0.12 로 올린다 — 다만 그러면 스킬 보유자가 많은 AI 구단(3~5명)이 플레이어(시즌 1 기준 1~3명)보다 더 깎여 시즌 1 우승률이 18.0% 로 올라간다(0.12 실측). 두 지표를 동시에 만족하는 값이 0.06 이었다.
- [ ] **속공 계열 3종(빠른 발·이동 공격·시간차)이 기계적으로 동일**하다. 엔진에 슬라이드/B퀵/C퀵 유형이 없기 때문이다. `AttackType` 에 `Slide` 를 추가하면 세 스킬이 갈린다(match-sim 14절의 "전위 스위치" 항목과 함께 검토).
- [ ] **각성 스킬(고유 스킬 II)** 미구현. training-mode 8.4 의 해금 조건만 있고 데이터가 없다. 같은 시스템에 `SKILLS` 항목을 추가하면 된다.
- [ ] **공용 스킬**(이벤트 획득, 최대 2개) 미구현. 선수 1명이 스킬 여러 개를 갖는 경우를 런타임은 이미 지원하지만(엔트리가 여러 개 붙으면 됨), 현재 `player.skillName` 이 1개뿐이라 데이터 구조를 배열로 바꿔야 한다.
- [ ] **AI 구단 스킬 레벨 사다리**는 season-check 7개 목표를 맞추려고 정한 값이다. `docs/league-and-economy.md` 의 사다리 `g` 재캘리브레이션과 함께 다시 볼 것.
- [ ] **UI**: `describeSkill(name, level)` 이 조건·수치를 한국어 줄로 만들어 주지만 `app-shell.html` 은 아직 설명 원문만 보여준다. 카드 상세에 "Lv3: 20점 이후 결정률 +0.68 로짓" 같은 줄을 붙일 수 있다.
